# 挑人框的搜尋與排序

> 狀態:計畫(2026-11-07)。來源標註:〔user〕= user 在對話中決定;〔提案〕= 我提出、user 看過比較表後同意方向;〔實作〕= 實作細節,我決定,可推翻。

## 問題

挑人的地方只有一個元件 `web/src/components/UserPicker.tsx`,13 處共用:分享 item、權限、發布、分享聊天室、排程「由誰執行」、群組成員與擁有者、我的資源(管理員替某人設額度例外)、skill hub 轉移、@提及、KB chat 分享(兩處)。

它現在:

- **沒有排序。** 清單照 `GET /users` 給的順序,而 `meta_routes.list_users` 原封不動照部署的使用者目錄(`UserDirectory.all_users`)回傳 —— 目錄怎麼排,畫面就怎麼排(user 看到的是照 id 排)。
- **搜尋不分好壞。** 名字、id、email、部門(`section`)任一欄「包含」輸入的字就算符合;打「王」時,名字開頭是王的人和部門裡剛好有王的人混在一起,仍照 id 排。

使用者回報:找人不好用。

## 外面怎麼做(查過的,2026-11-07)

| | 做法 | 出處 |
|---|---|---|
| 匹配度 | 開頭完全符合的排最前;符合的裡面,最近用過的再往前 | UI/UX Atlas(search UX and autocomplete) |
| 常用 | 看**多常**互動,不只最近一次 | Gmail(只有第三方說法,Google 未公開)、Microsoft Graph people API(依溝通與合作模式) |
| 情境 | 這則 issue/PR 的參與者優先 | GitHub changelog 2021-11;GitLab 參與者優先、再照字母;Zulip 最近對話過的人優先、再照字母 |
| 組織 | 依組織關係算相關的人,權重未公開 | Microsoft Graph |
| 移除 | 最近/建議的項目要標示清楚、可以單筆移除 | UI/UX Atlas、Gmail |
| 拼錯 | 容錯、發音相近 | Microsoft Graph(2016 部落格,可能過時) |

## 決定

### D1 排序要看的因素

- **搜尋匹配度、常用、組織遠近** 〔user〕
- **這次情境裡的人** —— 呼叫的地方可以傳一組「相關的人」〔提案〕
- 最後照名字 〔提案〕

### D2 常用:記在瀏覽器 〔user〕,看次數也看多久以前 〔提案〕

- 「常用」= **在任何一個挑人框裡選過**的人,不是打過的搜尋字 〔實作〕。
- 分數用 frecency(Firefox 網址列的做法):每個人記最近 10 次被選的時間,每次依距今多久給分 —— 4 天內 100、14 天內 70、31 天內 50、90 天內 30、更久 10 —— 加總 〔實作〕。
- 存在 `localStorage`,key 依登入的人分開(`peoplePicker.frecency.<userId>`),最多記 20 人,超過就丟分數最低的 〔實作〕。讀寫都包 try/catch;讀不到就當沒有常用,清單照其他規則排。
- 換電腦、換瀏覽器、清除網站資料就沒了 —— user 選瀏覽器時已知道這點。

### D3 組織遠近 = 部門字串的相近程度 〔user:「相近:字元相近」〕

- 算法:看的人自己的 `section` 和對方的 `section`,**從開頭算起相同的字元數**,越多越近 〔實作〕。
- 理由:目錄只有 `section` 一個欄位、沒有層級也沒有主管;有層級的部門代碼(「RD-PI-TF」、「研發處製程整合部」)開頭相同的越長通常越近,不必知道分隔符號。
- 看的人的部門取自 `useCurrentUser()`;沒有部門的人,對誰的遠近都是 0。

### D4 情境裡的人(`related`)〔提案,第一批由我決定 〔實作〕〕

`UserPicker` 加一個選填的 `related?: string[]`。第一批傳的:

| 呼叫處 | 傳什麼 |
|---|---|
| @提及(`AgentPanel`) | 這個聊天室裡發過言的人 |
| 排程「由誰執行」(`RunsAs`) | 這個 item 的成員(擁有者 + 權限裡點名的使用者) |
| 分享聊天室(`ShareChatDialog`) | 同上 |
| 發布(`PublishDialog`) | 同上 |

其他 9 處先不傳;它們沒有明顯的「這次相關的人」,硬湊只會讓順序更難預期。

### D5 排序規則 〔提案,細節 〔實作〕〕

由上往下比,前一項分出高下就不看下一項。

| | 還沒打字 | 打了字 |
|---|---|---|
| 1 | 情境裡的人 | 匹配度:名字開頭符合 > 名字中間符合 > id 或 email 開頭符合 > 其他欄位符合 |
| 2 | 常用(frecency 高的先) | 情境裡的人 |
| 3 | 組織遠近 | 常用 |
| 4 | 名字 | 組織遠近 |
| 5 | | 名字 |

- 名字用 `Intl.Collator("zh-Hant-TW")` 比 〔實作〕;中文名字照它的預設順序(若 user 要注音或筆劃,改這一行)。
- **清單在打開的那一刻定住常用分數** 〔實作〕:框開著時點選一個人,常用分數會變,但這次的清單不跟著重排 —— 點下去清單亂跳,比排序不完美更糟。已選的人照舊留在原位打勾。

### D6 常用要看得出來、可以移除 〔提案〕

- 還沒打字時,常用的人(最多 8 位)上方有一行小標「常用」;其他人在下方。
- 每個常用的人右側有一個 ×,按了就從這台瀏覽器的常用清單移除,不影響選取 〔實作〕。

### 不做

- **拼錯/發音相近的模糊搜尋。** 中文名字要先決定比注音、拼音還是字形,是另一個題目。
- **伺服器端記常用。** user 選瀏覽器。
- **改後端 `/users` 的順序。** 排序在前端做:常用和組織遠近都跟「誰在看」有關,目錄只有幾百人,前端已整份抓下來。

## 階段(每階段 /tdd 先紅後綠)

- **P1 排序函式**:`web/src/lib/rankPeople.ts`,純函式 `rankPeople(users, { query, viewerSection, related, frecency })`。表格式測試涵蓋 D5 每一列的勝負、名字排序、空部門、空查詢。
- **P2 常用紀錄**:`web/src/lib/peopleFrecency.ts`,讀、記一次選取、移除、上限 20、依登入者分 key、`localStorage` 讀寫失敗不擋。時間用注入的時鐘測。
- **P3 `UserPicker` 接上**:搜尋與排序改用 P1;打開時讀一次 P2 定住;選取(打勾)時記一次;「常用」小標與 ×。13 處的既有測試不能壞。
- **P4 `related` 第一批**:D4 表裡四處傳入;各一個測試證明那些人排在前面。
- **P5 文件**:`docs/subsystems/frontend.md` 記 `UserPicker` 的排序規則。無運營方動作,不寫 migrations。

## 怎麼驗證

- 單元測試(上面各階段)+ 突變探針:拿掉排序的任一層,對應的測試要紅。
- 真瀏覽器:兩種寬度(1280、390)各看一次清單、常用小標與 ×,看名字長、部門長時是否截斷得體。
- 錄 demo:同一個框,打字前後的順序、選一個人後下次打開跑到常用、按 × 移除。
