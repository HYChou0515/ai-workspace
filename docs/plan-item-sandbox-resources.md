# 每個 item 自己決定要開多大的環境

延續 [`plan-sandbox-resource-quota.md`](plan-sandbox-resource-quota.md)。那一份把資源綁在 **App**
上（一個 App 的每個 item 都一樣大），並加上每人跨 App 的總量。這一份讓**使用者自己決定
這一個 item 要開多大**，並且把「現在開著什麼、花了多少、怎麼關掉」搬到他正在看的頁面上。

需求三句話：

1. item 頁面顯示 sandbox 狀態、使用了多少 budget、以及關閉 sandbox
2. 使用者可以決定這個 item 的 sandbox 要開多少資源，由他自己的 budget 支出
3. 每個 App 可以設定上限，預設就是開上限

---

## 1. 定案的規則

以下每一條都是 grill 逐題拍板的，包含被否決的選項與理由。

### 1.1 選的是「上限」，不是「預約」

選了 4 核**不會**在當下從額度扣掉。額度只在 sandbox **活著**的時候被佔用——跟今天完全一樣。

開著三個 item 的頁面、每個都選了 2 核、但都還沒跟 agent 講過話 ⇒ **額度用掉 0**，因為
sandbox 是第一次 `exec` 才建立的。誰先動起來誰才佔額度。

> **否決「預約」的理由。** 預約在本質上就是 `admission.py` 明令禁止的那個計數器——它的
> docstring 寫著「帳是推導出來的、絕不用數的」，因為漏一次減法那格額度就永久蒸發，而且
> 看起來完全正常。這個專案已經在 soft-delete 上踩過兩次同一個坑。而且 cgroup 只在
> sandbox 存在時存在，預約沒有任何東西可以強制執行，它只是我們記在旁邊的一個沒有現實
> 對應物的數字。

代價（知情接受）：**選擇的當下不保證拿得到**。真的要跑時額度可能已經被自己別的 item
吃掉，那時才被擋。失敗發生在「我正要用」的時刻，那時使用者才有足夠脈絡理解為什麼。

### 1.2 只有 CPU 和記憶體，沒有硬碟

`_spec_for` 今天就只把兩個維度放進 sandbox spec；`disk_bytes` 走的是 `workspace_quota`，
因為**硬碟不是 sandbox 的資源**——它屬於工作區，比任何 sandbox 都活得久。

> **否決「讓使用者也調硬碟」的理由。** 關掉環境，CPU 和記憶體立刻歸還，檔案還在原地繼續
> 佔著。所以「把硬碟調小」沒有出口：使用者選了 1G、寫滿了、想改成 512M——我們要刪他的
> 檔案嗎？調不下去的選項就是假的選項。硬碟維持現狀：擋成長、縮小與刪除永遠放行，使用者
> 調整硬碟的方式是**刪檔案**，不是調數字。

### 1.3 預設 = `min(App 上限, 個人額度)`

「預設就是開上限」的「上限」有兩個，取小的那個。

> **為什麼不能只取 App 的上限。** `_enforce` 是 `live + incoming > limit` 就拒絕。App max
> 4 核而我的額度 2 核時，`0 + 4 > 2` ⇒ **這個 item 永遠開不起來**，關掉其他所有東西也沒用。
> 那不是「等一下再試」，是結構性的死路：畫面上一個看起來正常、按下去永遠 507 的 item。
> 預設值不該產生一個不可能成立的狀態。

即使兩邊都是 4 核（沒有死路），預設開滿仍讓「同時跑兩個 item」**一定會被擋**。這是對的，
不改——先前已拍板「撞到上限直接拒絕，不自動讓位」，而 4 核就是真的只夠一個 4 核的東西跑。
但它讓需求 #1 從加分項變成**必要條件**（見 §1.8）。

### 1.4 sandbox 活著時，數字是唯讀的

要改，先關掉。

> **否決「加一個 `resize` 協定操作」。** cgroup 的 `cpu.max` 技術上可以線上改，但這是一個
> 新的第一級協定操作——protocol / local / isolated / http / mock / sandbox-host 全部要實作，
> 而 `mark_ready` 那次證明這種東西還會牽出「改到一半失敗算誰的」。協定今天有 21 個操作，
> 沒有 resize。
>
> **否決「存起來、下次建立時生效」。** 畫面上會出現「顯示 1 核、實際跑 4 核」的雙重狀態，
> 而這個專案已經有一條血淋淋的紀錄（#720）：**紀錄＝信念，沒有東西對應現實**。

真正的需求本來就是「關掉」而不是「調小」：會想調小一個正在跑的環境，幾乎只有一種情境
——我在別的 item 撞到額度、需要生出空間——而那時我要的是**把它關掉**（立刻拿回全部），
不是調成 1 核（還是佔著，還得重啟才生效）。

任何時刻畫面上只有一個數字，而且它永遠是真的。

### 1.5 閘門是 `change_permission`，帳仍記 `owner`

| 條件 | 那兩個數字 |
|---|---|
| 有 `change_permission` ＋ sandbox 沒活著 | 可調 |
| 有 `change_permission` ＋ sandbox 活著 | 唯讀 ＋ 關閉按鈕 |
| 其他人（**含 agent**） | 唯讀（看得到，才知道為什麼被擋） |

> **為什麼是 `change_permission` 而不是 `write_meta`。** 決定性的理由不是「它最高」，而是
> **這個轉盤絕對不能落在 agent 手上**——這個 item 的 agent 就在這個 sandbox 裡跑，如果用
> 一個 AI 拿得到的動詞，agent 就能自己把自己的 CPU 上限調高、花掉 owner 的額度。
> `AI_FORBIDDEN = {change_permission, use_terminal}`，扣掉語意不對的 `use_terminal`，這是
> 被逼出來的唯一解——而它的語意剛好也對：能重新分配這個 item 存取權的人，就是它實質上的
> 管理者。

帳仍然記在 `owner` 頭上（沿用上一份計劃的決定，不重開）。所以會出現「A 有
`change_permission`，他調高，帳算 B 的」——這是自洽的：owner 主動把 `change_permission`
給出去，等於承認那個人是共同管理者，而且隨時可以收回。

### 1.6 `change_permission` 要能從前端授出去

後端**早就支援**明確授權（`grantsAnySubject(permission?.change_permission, ...)`，#608 之後
連 group 都能綁），但前端的分享 UI 從來沒有提供這個動詞：

```ts
/** ... change_permission / use_terminal are not offered in the UI */
export type ItemVerb = "read_meta" | "read_chat" | "read_content"
                     | "converse" | "add_content" | "edit_content" | "execute";
```

也就是說**那條授權路徑在後端是活的、在畫面上不存在**，實務上只有 owner 和 superuser 有它。
本計畫把它補進 UI，因為它現在已經不只是「誰能改權限」——它變成**「誰能花 owner 的錢」**，
一個有實質成本後果的角色，而一個有成本後果的角色卻只能靠改資料庫來指派，等於需求 #2
有一半沒做完。

⚠️ 它很重（被授權者可以再把權限轉給任何人），所以 UI 上**與其他動詞分開呈現、講清楚後果**，
不能混在現有角色清單裡當第八個 checkbox。

### 1.7 自由填，只擋 `> 0`

不是離散檔位，不設地板機制。

> **否決「離散檔位」的理由（user）：不夠自由。**
>
> **否決「量出映像的最小可用值當硬地板」的理由（user）：使用者自己把數字調低，因果關係
> 對他是明顯的，他會發現。** 不需要替他做決定。
>
> **否決「新增一個沒人會設的 `per_app.min` 設定鍵」的理由：** 那就是 #709 的形狀——上線
> 第一天沒有任何保護，而功能「看起來像沒做」。
>
> **否決「在 app.json 加 `min`」的理由：** 加了沒人會填的 App 欄位，功能就會像沒做（#709
> 的原始教訓）。

力氣改花在**讓後果看得見**：sandbox 真的因為記憶體太小起不來時，錯誤訊息要**指回那個設定
和那個值**（「環境無法以 64M 啟動——在資源設定調高」），而不是一個通用的啟動失敗。這樣
「他會發現」才成立；否則他發現的是「產品壞了」。

這也跟既有的不對稱一致：`cpu` 的 `0` 是「未指定」不是「零核心」，因為零核心不是任何人的
本意。

### 1.8 撞牆的那一刻要是一扇門，不是一面牆

§1.3 之後撞牆從例外變成常態，所以這一刻的體驗**就是這個功能的體驗**，不是錯誤處理的邊角。

今天使用者看到：`cpu 4 of 4 already in use by live environments`。他知道滿了，但不知道
**是誰佔著**，也不知道**關掉哪一個夠**——得自己想到有 `/my-resources` 這頁、切過去、
看清單、關掉、切回來、重打一次訊息。

`SandboxQuotaExceeded` 的 docstring 自己說了「the only useful thing to tell someone is
**what to close and how much it buys back**」，但它只帶 `dimension` / `used` / `limit`，
**沒帶是哪些 item**——那句話只做到一半。

資料我們手上都有（`live_for(owner)` 每一列都帶 `item_id`，`/me/resources` 更是連 `title`
都有）。所以拒絕訊息要能說：

> 你的 4 核已經用完了。目前佔著的是「晶圓良率分析」2 核、「客訴分類」2 核。
> 關掉其中一個就能繼續。

而且**關閉按鈕就在那裡**——`DELETE /me/resources/live/{item_id}` 已經存在、#720 已經驗過
它真的會關掉。不需要換頁。

範圍限定：**只做「說出是哪些、就地可關」**，不做自動讓位（先前已拍板不自動讓位）。

⚠️ 這句話會**洩漏 owner 其他 item 的標題**。owner 自己看沒問題；協作者驅動 turn 而撞到
owner 的額度時，訊息**退化成不指名的版本**（「這個 item 的擁有者額度已滿」）。

### 1.9 永遠不存預設值

item 建立時**不**把 `min(App, 額度)` 算好存進去。欄位是**可選的**，空 = 未指定 = 用當下
算出來的值。

> **理由是 SSOT，而且是 user 自己在別的議題上定的原則**（他否決在 aiw 設
> `history.context_limit` 時說「這違反 SSOT」——那是一份會漂移的副本）。存下來的話：管理員
> 把我的額度從 2 核調到 8 核，我三個月前建的 item 還是停在 2 核，**而且畫面上看起來完全
> 正常**；反過來額度調降時那些 item 還記著舊的大數字。

跟既有慣例一致：`AppResources` 每個欄位都是「absent ⇒ 往下一層掉」。

副作用（好的）：schema 是 `WorkItemBase` 上兩個**可選**值，不用 migration、不用 backfill，
也不踩 `indexed_data` 那個坑（這是對 item 點查，不是查詢條件）。

⚠️ **前提條件（user 明確要求）：前端 UI 必須清楚。** 見 §3 驗收條件的「看得見」那組。

### 1.10 存檔走自己的路徑，不跟其他欄位一起

`PUT /a/{slug}/items/{item_id}/resources`，gate 在 `change_permission`。清空 = 回到預設。

> **否決「塞進一般的 item 更新」的理由。** 那會變成：同一個存檔動作裡大部分欄位只要
> `write_meta`、其中兩個要 `change_permission`，得在裡面對單一欄位做特例檢查。這是
> **「一條規則寫在兩個地方」**的教科書案例，而那正是上一份計劃四輪 review 歸納出的**復發
> 形狀**。而且欄位級檢查很難被測試釘住：漏掉它，一般 PATCH 照樣成功，所有既有測試全綠。
>
> **先例：** `PUT .../members` 已經因為同樣的理由被拉出來走 `change_permission`——
> 「編輯成員現在會授予存取權，所以**不再是普通的 `write_meta` 欄位編輯**」。我們這兩個
> 數字是同一種東西：看起來是欄位，實際上是在動錢。

### 1.11 面板拆成兩半，各自的前提條件

出廠預設 `PerUserResources` 四個維度全是 `0`/`""` ⇒ `_configured()` 為 `False` ⇒ **准入閘門
整個是 no-op**；而「P1–P9 做完後沒有任何 App 宣告 `resources`」。所以照 §1.1–1.10 直接做完，
在一個沒特別設定過的部署上會是：轉盤上限「無限」、budget 儀表「0 / 0」——**上線了但看起來
像沒做**。

| 半邊 | 顯示條件 | 理由 |
|---|---|---|
| **狀態 ＋ 關閉環境** | 這個 App 有 sandbox 能力 | 「我的環境在跑嗎、關掉它」跟額度**完全無關**，就算部署不管額度也有價值 |
| **budget ＋ 轉盤** | 部署有設額度（`_configured()`） | 沒有額度就沒有「花費」這回事。畫「0 / 0」是雜訊；給一根上限無限的桿子更糟 |

這樣需求 #1 的核心價值在**預設部署上就看得見**，不必等維運者先去設額度。

### 1.12 狀態與用量的資料來源

**不新增逐 item 探測。** `GET /me/resources` 的 payload 已經包含
`live: {item_id, slug, title, cpu_cores, memory_bytes}[]` 以及 `cpu_in_use` / `memory_in_use`
/ `limits`——「這個 item 活著嗎、佔多少」只是 `live.find(e => e.item_id === X)`，**跟總量
同一份 payload**。

> **為什麼不用 `has_live_sandbox(item)` 逐 item 探測：** http 後端那是一趟真的網路往返，
> 而且沒有必要。`live[]` 從心跳推導，跟 `admission.check` 讀**同一個來源**——所以面板顯示
> 的東西跟閘門判斷的東西**天生一致**，不可能出現「面板說沒東西在跑、閘門卻擋你」。這比
> 探測更好。
>
> **為什麼總量不能藏到 tooltip 後面（user 一度考慮）：** 分開反而更貴。總量跟這個 item 的
> 數字是同一次查詢的產物，延後載入會變成兩次呼叫，而且重新引入 payload 註解明講過的缺陷
> ——分開拿會渲染出「從來沒有同時成立過的一對數字」，畫面出現「3 of 2 used」看起來就是 bug。

`running_items()` **只能用來「找東西」，不能用來「斷定沒有」**（hosted 後端只答接到請求的
那個 replica，失敗時回 `None`）。本計畫不使用它。

⚠️ **缺口：`live[]` 是 owner 範圍的。** 協作者看別人的 item 時這份 payload 裡沒有它。
補一個 `GET /a/{slug}/items/{item_id}/environment`，gate 在 **`read_chat`**，只答**這一個
item** 三件事（在不在跑、佔多少、這個 item 設定的值），**絕不回傳 owner 的總量**。

> **為什麼是 `read_chat` 而不是 `read_meta`：** `read_meta` 的人只在 dashboard 清單上看到
> 標題，**根本進不去那個頁面**——給他這份資料買不到任何東西，卻多開一條回答「別人的環境
> 現在跑著多大」的路。**沒有消費端的授權就是純粹的攻擊面。** `read_chat` 的字面意思就是
> 「可以進入這個工作區」，閘門跟它守護的畫面對齊，最不會漂移。會撞到 507 的
> Participant 本來就包含 `read_chat`。

### 1.13 UI 是持續設定，不是建立時的提問

面板長在 item 頁面上，還沒開始跑之前可以調。**不做**「建立 item 時跳出來問你要多少資源」
——那會在使用者還沒做任何事之前先丟一個資源問題給他，而九成的人會直接按預設。

### 1.14 從上面推導出來的（不需另外拍板）

| # | 事項 | 做法 |
|---|---|---|
| 1 | 存的值後來被上限追過去 | 讀取時夾住，但**明說**：「你設 4，實際生效 2（受你的額度限制）」。絕不靜默截斷——`_enforce_ceiling` 已是這個態度 |
| 2 | `min(App, 額度)` 誰在綁 | UI 要講出來，否則使用者跑去調錯的那一邊 |
| 3 | App 沒有 sandbox 能力（`function.sandbox: false`） | 整個面板不出現，不是一個永遠「未啟動」的空面板 |
| 4 | 排程 / headless workflow | 用 item 的值，沒有人可以問。行為與有人在時一致 |
| 5 | 「回到預設」 | 清空欄位（§1.9 的必然結果） |
| 6 | 記憶體輸入格式 | 沿用既有 `parse_size`（`512M` / `2G`），不另發明 |
| 7 | 關閉環境之後 | 轉盤變成可編輯 |
| 8 | 兩個有權限的人同時改 | 最後寫入者贏。這是設定欄位，可接受 |

### 1.15 准入閘門不用改一行

`would_cost(item)` 走 `effective_limits(self.spec_for(item))`，而 `_spec_for` 正是轉盤要接進去
的地方。轉盤一接上，閘門算的「這個新 sandbox 要花多少」自動跟著變。

這符合上一份計劃歸納出的防線：**一條規則只有一個地方能回答**。

## 2. Phases

### P1 — 每個 item 自己的值，接進 `_spec_for` ✅

`WorkItemBase` 兩個可選欄位；`_spec_for(item_id)` 從「只讀 App 上限」改成
「item 的值（有的話）否則 `min(App 上限, owner 額度)`」，讀取時夾住。

**驗收（每個維度各一條）**
- CPU：item 設 1 核、App 上限 4 核 ⇒ 建立出來的 spec 是 1 核（**不是** 4）
- 記憶體：item 設 512M、App 上限 2G ⇒ spec 是 512M
- 空欄位：兩個都不設 ⇒ spec 是 `min(App, 額度)`，且**額度改變後這個值跟著改**（釘住 §1.9）
- 夾住：item 設 8 核、額度 2 核 ⇒ spec 是 2 核
- **沒有任何 App 宣告 `resources`** 的設定下，以上五條全部重跑一次（#709 的教訓）

### P2 — 存檔路徑與權限 ✅

`PUT /a/{slug}/items/{item_id}/resources`，gate `change_permission`；清空 = 回預設。

**驗收**
- 只有 `write_meta` 的人 ⇒ 403/404，而且**item 的其他欄位仍然改得動**（釘住「沒有把一般編輯一起鎖死」）
- agent 拿不到這個動詞 ⇒ 走 agent 的路徑改不動（釘住 §1.5 的決定性理由）
- owner / superuser / 被明確授權者 ⇒ 改得動
- 清空 ⇒ 回到 `min(App, 額度)`

### P3 — 讀取端點（協作者用）✅

`GET /a/{slug}/items/{item_id}/environment`，gate `read_chat`，只答這一個 item。

**驗收**
- 只有 `read_meta` ⇒ 403/404
- `read_chat` ⇒ 拿得到狀態、用量、設定值
- 回傳內容**不含** owner 的總量或其他 item（釘住 §1.12 的不洩漏）

### P4 — item 頁面面板 ✅

兩半（§1.11）。主角是**這個 item 佔多少**，總量在旁邊當脈絡。

**「按得動」驗收**
- sandbox 沒活著 ⇒ 數字可調、寫「下次啟動時使用 X」
- sandbox 活著 ⇒ 數字唯讀、關閉按鈕可按、按了真的關掉
- 沒有 `change_permission` ⇒ 唯讀

**「看得見」驗收（分開列，#709 的教訓 3）**
- 空欄位**不得**渲染成 `0` 或空白框，必須是「4 核（預設，依你目前的額度）」
- 明確設過 vs 未指定**一眼可分**，不是靠數字大小去猜；有「回到預設」
- 被夾住時**兩個數字都在**（你設 4／實際生效 2）且**說出是哪一邊在綁**
- 部署沒設額度 ⇒ 只有「狀態＋關閉」那半邊，**沒有 0/0 的儀表**
- App 沒有 sandbox 能力 ⇒ 整個面板不出現
- **真瀏覽器實測**：面板有 CSS、gauge 不是零高度 div（#709 踩過）

### P5 — 拒絕訊息就地可行動 ✅

`SandboxQuotaExceeded` 帶上佔用清單；507 的回應與 UI 顯示「是哪些 item、各佔多少」＋
就地關閉按鈕。協作者情境退化成不指名版本。

**驗收**
- owner 自己撞到 ⇒ 訊息列出佔用的 item 標題與各自用量，按鈕可關且關完能重試成功
- **協作者撞到 owner 的額度 ⇒ 訊息不含任何 item 標題**（釘住 §1.8 的洩漏防線）
- 每個維度各一條：`count` / `cpu` / `memory` **單獨**把人擋下來時，訊息都指名該維度
  （#709 的教訓 1：不准用一個維度代表其他維度）

### P6 — 前端補 `change_permission` 授權 ✅

分享 UI 加入這個動詞，與其他角色**分開呈現**、講清楚後果。

**驗收**
- owner 可以把 `change_permission` 授給某人／某 group，該人隨即改得動資源
- UI 上這個授權與 Participant 等角色**視覺上分離**，且有後果說明
- 撤銷後該人立刻改不動

把結果傳到前端。

**驗收**
- 後端不套 cpu ⇒ CPU 桿子不出現，改成一行說明
- **後端說不出來 ⇒ 說「無法確認」，不說「已套用」**（#712 修過的那條線不能在 UI 上斷掉）

嚴重的那些不用計數表示，因為列得出名字：**額度或權限可以被繞過**的有六個——generic PATCH 與
create 兩道沒守的門（§6.1）、活著時改大小讓 7 核算成 3.1（§6.1）、刪掉 item 就放掉名額（§6.8）、

### 6.1 一再重演的那個形狀

> **規則被裝在「我當時在看的那個地方」，而不是「值真正被寫入／被讀取的地方」。**

| 我以為守住了什麼 | 實際上 |
|---|---|
| 「調整大小需要 `change_permission`」 | 我加了一條專屬路由，**欄位卻長在 `WorkItemBase` 上**——specstar 的 generic PATCH 用 `write_meta` 就寫得進去，而 `authorize` 對 public item 的 `write_meta` 是無條件放行。第三道門是 auto-CRUD create，完全沒閘。 |
| 「sandbox 活著時唯讀」 | 只 disable 了輸入框。後端照收，而心跳每次重讀 `spec_for` ⇒ **帳按新值算、cgroup 是舊值**。實測跑著 7 核只算 3.1，每個 item 重複一次額度等於無限。 |
| 「推導出的天花板太小就拒收」 | 只裝在 `history_budget`，而天花板有三個讀者（#767 的同一課，我在這裡又踩一次的變體）。 |

**防線不是更仔細地讀，是先數讀者。** 修這類缺陷前先
`grep` 那個值有幾個消費端，判準放在**值被產生出來的地方**做成共用函式。

### 6.2 我的修正自己壞掉（第二輪）

四個嚴重缺陷修完之後，regression review 發現**其中兩個修法本身是壞的**：

- **一個屬性名打錯**（`context.current` vs `current_resource`）讓每一個 App 的每一次整物件寫入都被當成特權編輯，一般使用者按「關閉」拿到 **500**。
- **commit message 宣稱「兩種 patch 格式都涵蓋」是假的**：specstar 傳的是純 list，我卻去拿 `.patch` 屬性 ⇒ RFC 6902 整條分支是死碼。而**前端真正送的就是 6902**，且它連既有的 `permission` 閘門都繞得過（提權）。

那條本該擋住它的既有測試傳的是真的 `jsonpatch.JsonPatch` 物件，**而 specstar 從來不傳那個形狀**——替身跟缺陷一起錯。

### 6.3 兩個「做完＝看得到」的失敗

- **P5 的就地關閉 UI 從來沒有被渲染。** 元件、解析器、單元測試都在，沒有任何地方接上去，而我在進度回報裡說它做好了。
- **P7 的「無法確認」在 `kind: local` 永遠不觸發**：我用非空的 spec 去問 `effective_limits`，而那個後端原樣回傳。我的測試替身無條件回 `None`，沒有模擬真實後端的契約。

### 6.4 測試自己是裝飾品的兩次

兩條測試**寫完就綠、突變也殺不掉**：

- 「pod 忘記 session 之後大小還能改」——旗標設得太晚，teardown 自己的 walk 已經回報目錄消失，探針從沒看到那個狀態。改成一開始就設之後，舊碼紅、新碼綠，兩邊都驗過。
- 「標題查詢有批次化」——它看得到的呼叫被 admission 閘門和 fact memo 蓋過去了。**這條我直接刪掉**，把量測數字和理由留在原地：一條殺不死的測試會宣稱它沒有的保護。

### 6.5 第三輪：修正的修正又壞了

第二輪修完之後再開一輪，**又是 7 個**，而且前兩個還是**同一個修正**的問題：

- **我硬寫了 120 秒，並在 docstring 宣稱「跟 admission 閘門同一個視窗」。** 實際上閘門用的是
  `idle_timeout`（預設 **8 小時**，240 倍），而 `sandbox_activity` 自己就寫著規則
  （「視窗要等於 reaper 的閒置門檻：太短會少算一個閒置但仍佔著記憶體的 sandbox」）。心跳只在
  使用時更新，所以**模型想三分鐘**就足以讓執行中的 sandbox 讀起來像停了、409 解除——正是那條
  拒絕存在的理由。**我編了一個數字，然後寫了一句話宣稱它不是編的。**
- **我用 `owner_of(item)` 去查心跳**，而 `owner` 是誰都能 PATCH 的欄位 ⇒ 改一次就解鎖。
  **這道門是我自己開的**，舊的 `has_live_sandbox` 沒有這個依賴。
- **那個修正只做在後端**：路由解除了，而面板是用另一個欄位 disable 輸入框的 ⇒ 使用者按了關閉、
  畫面依然是灰的。**同一個問題兩個答案，就是螢幕和伺服器開始各說各話的方式。**

另外三個：`math.isfinite` 對 309 位數的 int 丟 `OverflowError`（一個為了避免「看不懂的錯誤」
而加的檢查，變成看不懂的 500）；`bound_by` 一個純量代表兩個維度會歸錯因；軟刪除的 item 整列
從 `holding` 消失，而它正是唯一能關的東西。

最後一個是**先於這個分支**的：`GET /me/resources` 列環境時完全不檢查 `read_meta`，所以我在
507 上做的遮蔽，隔壁一條路由就破功——**而那條路由正是拒絕訊息叫人去的地方**。一條在這裡成立、
在隔壁不成立的規則，不是規則。

### 6.6 第四輪：學到的教訓，在隔壁檔案又犯一次

第三輪修完再開一輪，又是 5 個。最值得記的是這個：

**第二輪我因為「每列一次沒快取的權限查詢」被抓（N+1，跑在 async handler 裡的同步 specstar
I/O）。我修了它、把教訓寫進 commit message、寫進這份文件——然後在第三輪，於隔壁的
`quota_routes.py` 用同一個 `require_item_access` 做了一模一樣的事。**

實測：20 個工作區時 `find_work_item` 40 → 60、group 查詢 0 → 20，而那份清單長度沒有上限。
更難堪的是，**那個檔案裡就有一段警告寫著同一個形狀**（#657，「一次頁面載入量到 42 次」）。

這不是「沒學到」。這是 §6.1 那個形狀的第四次變體：**規則被裝在我當時在看的那個檔案裡。**

其餘四個：加抽象方法沒更新測試替身（**CI 直接紅了而我沒發現**）；一個軟刪除的 item 讓整個
`/me/resources` 回 410（比上一輪修的那個更糟——連健康的列都沒了，而那頁正是關閉按鈕所在）；
`memory_bound_by` 送出去了卻沒人渲染（**上一輪才剛修過「只做在後端」**）；以及兩個機制的
測試殺不掉突變，其中一條的名字還在描述已被移除的機制。

順帶一提，我在引用「flat integer 絕不用 1a/1b」那條規則的同一個 commit 裡，把這一節編成了
`6.4b`。

### 6.7 第五輪：我守了三個查詢裡的一個

第四輪那個「軟刪除的 item 讓 `/me/resources` 回 410」我修了——修在 `_describe` 上。
同一個請求還有另外兩次 `find_work_item`，其中 `_found_running` 是**先掃過這台機器上每一個
sandbox（每一個租戶的），才做 owner 過濾**。所以一個人刪掉自己的 item，會讓**同一個 pod 上
其他所有人的 `/me/resources` 一起 410**——不需要心跳遺失，不需要視窗過期。

我那一輪自己寫的測試是綠的，因為它從**刪除者本人**的視角寫：他自己那一列會在走到那個查詢
之前就短路掉。第二個發現是同一件事的下一步——我上一輪才剛讓那一列「看得見」，而它上面
那顆關閉按鈕按下去回 410。我的 docstring 才剛寫著「叫不出名字的環境仍然關得掉，看不見的
不行」。它關不掉。

### 6.8 第六輪：把「找不到」和「不用付錢」壓成同一個值

第五輪我把那個 seam 改成「軟刪除 ⇒ 回 `None`」。頁面修好了，**額度垮了**：有四個消費端把
`owner is None` 讀成「沒有人要付這筆」——准入閘門直接 return、個人磁碟上限直接 return、用量
不記錄，而最糟的是 `registry._bump` 會把 `owner=""` **蓋回一列本來有名字的帳本**。

reviewer 給的重現只要四個呼叫：exec A → 200、exec B → **507**（額度滿）、刪掉 A → 204、
再 exec A → 200（**owner 被抹掉**）、exec B → **200**。兩台 sandbox 都在跑，帳掛在沒有人身上，
`/me/resources` 也就再也看不到它——沒有人知道要關掉什麼。

**而我對這個缺陷的第一版修法，錯在相反的方向。** 我讓 seam 無條件讀得到刪除列，並且在
docstring 裡寫「需要拒絕刪除 item 的呼叫端自己會擋，每條手寫路由都有 access gate」。
那句話是假的：access 是從 item 記錄上讀出來的，而記錄現在讀得到了。`require_item` 又正好是
每一條 `/a/{slug}/items/…` 的守門，所以 exec、resize 全都對一個已刪除的 item 回 200。

真正的形狀是：**「還欠這台機器的錢」和「還能操作」是兩個問題，由呼叫端指定問哪一個。**
`include_deleted` 只給回答第一個問題的三條路徑（債務人、環境大小、資源頁），預設仍然是
「找不到」——那既是路由要的，也是不讓一次刪除 410 掉別人的原因。

這次是我自己抓到的，方法是**寫一條測試去驗我 docstring 裡那句話**。

### 6.9 CI 抓到 review 沒抓到的：404 和 410 是兩件事

第五輪那個「軟刪除 ⇒ 回 `None`」還打破了一條**既有的對外契約**：#700 的外部系統會先列出
item 再操作，所以「上傳到已刪除的 item」必須回 **410 Gone**，讓對方分得出「那個 item 結束了，
開新的」和「平台壞了，等一下重試」。變成 404 之後，對方最可能遇到的競態看起來像故障。

**六輪 review 沒有一輪抓到它，CI 抓到了**——因為那條測試早就存在。這正好是 CLAUDE.md 那句
「review 和 CI 回答的是不同問題」的反向例證：review 找的是沒人寫過測試的缺陷，而 CI 守的是
**已經寫下來的承諾**。我在第五輪把承諾改掉卻沒發現，是因為我沒讓那一輪的 CI 跑完。

修法讓規則變得比原本更清楚：

> **操作單一 item ⇒ 已刪除回 410；跨多個 item 的清單／帳務頁 ⇒ 永不 410。**

而第一次修的時候，我又只裝在**我當時在看的那兩個閘門**上（locator 的 `require_item` 與
`require_access`），漏掉 `item_authz.require_item_access`——手寫 item 路由用的正是它。
是我自己的測試紅了才抓到。現在三個閘門呼叫同一個 `refuse_if_gone`。

### 6.10 第七輪：兩個「額度可以被關掉」和一個 fail-open 權限

第六輪修完再開一輪，5 個 CONFIRMED，其中兩個是**把額度整個關掉**的路徑，而且都不是刪除造成的：

- **把 `owner` PATCH 成空字串。** #687（`owner` 誰都能改）是已知取捨，但 §4 把它記成「把帳指向
  自己、再把數字調大」——帳會**搬家**。清空是另一回事：`_owner_of` 回 `None`，四個閘門同時
  讀成「沒有人要付」，一個 item 一次 PATCH 就能多開一台，而且那台不會出現在任何人的資源頁上，
  也就沒有人看得到要關掉它。修法是**空的 `owner` 落回 `created_by`**（specstar 自己寫的、任何
  路由都改不到），所以「沒有人」這個答案消失了，而 `owner` 有值時仍然優先。
- **`kind: local` 下跑過一次的 item 永遠不占名額。** 准入閘門問的是
  `registry.has_live_sandbox`，沒有位址表時它退化成「這個 item 的目錄還在嗎」，而那些目錄會
  活到八小時後的回收。**我在 `set_item_resources` 已經否決過同一個來源、改用心跳，還把量測寫進
  docstring**——判斷沒有跨過一個檔案。現在閘門讀的是**它馬上要計算的那張帳本**，「有沒有占著
  名額」和「占了多少」不可能再互相矛盾。
- **軟刪除 item 的新 chat 被蓋成 public。** `item_conversation_mirror` 把「找不到」讀成「沒有
  限制」，於是私有 item 的討論串變成任何人可讀，而且**永久**——item 已經刪了，改權限時的 fan-out
  再也跑不到它。這是第五輪那個 `None` 的另一個消費端，我做分類的時候漏掉了它。

另外兩個是註解裡的假數字（「只有一個呼叫端」其實兩個、「除此之外沒有別的」少算一個），以及
帳本 backstop 在 `restore` 分支上不成立——**而既有那條測試正好走過那個分支，卻只斷言時間戳**。

review 還指出一件我自己補的：同一個問題有兩條相反的規則各自寫在自己的 docstring 裡——資源頁
把「你看不到但你在付錢」的列保留成不具名，507 拒絕訊息卻直接丟掉。兩套並存就是保證其中一套
會變成假的。統一成保留。

### 6.11 第八輪：我寫了共用函式，然後在最需要它的閘門沒有用

上一輪我把「已刪除 → 410」收成一個共用的 `refuse_if_gone`，並在檢查表第 10 條寫下
「判準要收成一個共用函式，讓『漏掉一個』變成不可能」。然後在 `locator.require_item`——
唯一沒有存取檢查、最容易洩漏的那個閘門——**手刻了第二份**。

那份問錯了問題：它問「這個 id 解析得到嗎」，不是「它被刪了嗎」。於是**整條 slug 不符的分支
開始回 410 Gone**：

```
correct slug, no access -> 200
wrong slug, live item   -> 410  ← 活著的 item 被說成「結束了」
wrong slug, unknown id  -> 404
```

四件事同時錯：item 根本沒死；`require_item` 不做任何授權，所以任何人都能靠 410/404 分辨
「某個 App 有這個 id」；它牴觸我自己剛寫的「410 只給看得到的人」；而 `tools_routes.py` 的註解
還寫著「404s a wrong slug→item pairing」。**沒有任何測試釘著 wrong-slug → 404**，所以全綠。

另一個：R7 那個 `created_by` floor 我寫成 `if item.owner:`——**truthiness 不等於「有沒有說出
東西」**，一個空格就走過去，額度整個關掉的缺陷原封不動回來。改成 `.strip()`，並把測試
parametrize 成 `""` / `"   "` / `"\t\n"`。

其餘三個是**註解和程式碼說反話**：`_owner_of` 的 docstring 還寫著「Deliberately NOT
`created_by`」（那正是它現在做的事）、`admission` 與 `sandbox_activity` 同樣沒跟上、
507 訊息裡那段「看不到的列會被略過」在我上一輪改成保留之後就成了假的。

review 另外指出一個我確認為真的：`change_permission` 代理人**關不掉已刪除 item 的環境**——
`slug_of` 不讀刪除列給出 `""`，而 `require_item_access` 又對刪除的 item 回 410，兩重拒絕，
偏偏那正是這頁 docstring 主張最用力要能關掉的那一列。**關閉是帳務動作不是操作動作**，
所以它改用帳務那個視角解析，並刻意不因為「已刪除」而拒絕。

突變探針這一輪又自己錯了三次（打在 slug 檢查之後、`replace(...,1)` 命中同檔案第一個
`load_access_facts`、挑到走別的閘門的測試）。第三個順帶揭露真東西：**`require_item` 的 410
當時沒有任何測試釘著**——走它的只有 tools / capability / entity 三組路由，而我的測試全走另外
兩個閘門。補上之後 4/4 killed。

### 6.12 第九輪：沒有 BLOCKING，但兩個修法自己又漏了

第八輪之後開的第九輪，**沒有 BLOCKING**，三個 SERIOUS 有兩個是上一輪修法本身：

- **`debtor_of` 用 strip 過的值判斷、卻回傳原值。** `owner = "alice "`（一個尾隨空格）記在
  `"alice "` 頭上，而帳本是精確比對 ⇒ 額度整個關掉、環境不出現在真正 owner 的頁面上，
  **和 R8-2 一模一樣的結局**，只是這次完全看不出來（UI 每一處都顯示「alice」）。
  上一輪我補的 parametrize 只試了純空白，沒試「有內容但被墊過的真名字」。
- **`require_item` 每次成功都多付一次 store 讀取**，而且我給的理由是假的。我寫
  「`require_access` 也付一樣的兩次讀取」——它有 5 秒的 facts 快取，窗內付零；而每條 chat 路由

  `turn-alive` 從 3 get + 3 meta 變成 3 + 4。這個 repo 自己記著一次往返約 219 ms。
  改回「成功路徑一次讀取，只有 miss 才載 facts」，五種情況的答案完全不變。
- **我拿掉一份手刻的閘門副本，同一個 commit 又加了一份。** 關閉路徑內聯了
  `require_item_access` 的身體（減掉 `refuse_if_gone`）。想要的差別是**參數**不是拷貝：
  `slug=None`（這條路由本來就沒有 slug）與 `allow_deleted=True`（關閉是帳務動作）。
  順帶一提，內聯那版還把 `load_access_facts` 放在 `try` 外面，store 出錯會變成 500。

另外兩個是註解：`refuse_if_gone` 宣稱「一定在存取檢查之後」，但 `require_item` 根本沒有存取
檢查（那三組路由是既有的無授權漏洞，已寫明而不是拿來當藉口）；心跳那列的 owner 註解寫成
「寫入當下解析的」，但 backstop 會讓它是更早一次的值——而**「這個數字有多舊」正是讀帳本的人
最需要知道的事**。

順手修掉一個 review 標為 speculative 但確實會 500 的 race：`tools_routes` 在閘門通過後
重新解析一次 item，中間若有人刪掉就是裸的 `AssertionError`。

### 6.14 第十一輪：沒有使用者碰得到的東西，但三個發現全是同一個根因

第十一輪**沒有任何使用者或維運碰得到的缺陷**。三個發現全是內部的，而且是同一個根因：
**我三次憑記憶宣稱「哪條路由走哪個閘門」，三次都錯。**

正確的表已經寫進 `item_authz.py` 的 module docstring（grep 出來的，不是想出來的）：

| 閘門 | 路由 |
|---|---|
| `require_item_access` | `/resources` `/environment` `/permission` `/members`、item PATCH、env-provider、`DELETE /me/resources/live/{id}` |
| `ItemLocator.require_access` | `/exec` `/files` `/chats` 與 streams（59 處） |
| `ItemLocator.require_item` | `/tools` `/entities` `/export`——只驗 slug 配對，**不授權任何人** |

由這張表推出來的三件事：

1. 我在 §6.13 寫的「拿掉 `check_access` 的比對只有 `/tools` 會紅」是假的。`/tools` 走
   `require_item` 自己那份,到不了 `check_access`。**真實情況更嚴重**——`check_access` 的
   slug 規則當時零測試。
2. 我那條新測試的註解把 `/environment` 說成走 `require_access`，其實是 `require_item_access`：
   `resources` 和 `environment` 是**同一個閘門**，只有 `exec` 是另一個。
3. 「slug 規則住在兩個地方」是**真的**，而且是它測不到的原因。現在收成一個 `app_matches`，
   一次突變同時殺掉兩邊。第二個 carrier 存在有正當理由（`require_item` 只讀一次、不需要權限
   facts），所以共用的是**判準**而不是整段流程。

另外那條測試在突變下**第一個請求就丟例外**，後兩個斷言根本沒跑到——所以「驗過會紅」只證明了
三分之一。改成三個閘門各自獨立取狀態、最後一次比對整個 dict。

以及一個 dead branch：`ANY_APP` 那條 404 訊息永遠不會被看到（唯一的呼叫端把所有拒絕都映射成
「unknown environment」）。刪掉，不留分支。

### 6.15 第十二輪：把每個守衛刪掉,看有沒有測試會紅

前十一輪都是「找缺陷」。第十二輪換了問法——**這個分支加的每一個守衛,刪掉之後有沒有任何測試會
紅?** 這等於直接去找我沒走 TDD 的地方,而它找到的東西比前面幾輪加起來都準。

**唯一維運碰得到的:`ItemLocator._access` 是無上限的快取。** 這個分支新加的(master 的
`require_access` 直接轉呼叫、不快取),行程生命期內每個被 gate 過的 item 存一份完整記錄,5 秒
視窗只決定「可不可信」不決定「留不留」,而 `forget_access` 只有一條路由會呼叫。它的兄弟
`_item_facts` 就在隔壁檔案,有 `_ITEM_FACT_MAX` 和一句註解寫著「bounded: this is a cache, not
a map」。**同一條規則兩個 carrier,只有一個有。** 而且我補的時候發現第二個 memo(`_groups`)
也是同樣情況——一次補兩個。

**最尖銳的方法論發現:有兩條測試的名字就叫那個守衛,而它們是靠別的東西才綠的。**
`test_an_item_with_no_resolvable_owner_is_not_gated` 和 `test_no_configured_limit_never_refuses`
刪掉對應的 early-return 之後照樣通過——一個是因為樁函式忽略參數,一個是因為 `_enforce` 自己的
`if limit and …` 接住了。**這比沒有測試更糟:它讓人以為守著。** 修法是斷言那個守衛真正買到的
東西——「額度沒設定或沒有債務人時,閘門根本不該去查帳本」。

**影響最大的無測試守衛:`_is_live_sync` 的 `last_active_ms >= since_ms`。** 它壞掉的話,過期
心跳會被讀成活著 ⇒ 准入閘門提前 return ⇒ 那個 item 的 per-person 額度**完全不執行**,而且
resize 的 409 永遠不解除,叫人去關一個幾小時前就停掉的環境。

**四個死守衛,全部是「新規則下沉沒刪舊規則」:** `math.isfinite`(後來加的 `_MAX_*` 已涵蓋,
而 docstring 還在長篇論證它的順序)、`live_for` 的自我排除(我第七輪把 `is_live` 移到它上面
之後就死了)、`_owner_of` 的 `or None`、`ItemLocator.owner_of` 的兩個冗餘。每一個都補上
「它為什麼死了、什麼改動會讓它復活」,而不是靜靜刪掉。

**那張閘門表又錯了。** 上一輪我說它是 grep 出來的——它列了不存在的 item PATCH、漏了
`/close`、也漏了 `require_chat → require_item` 讓所有 chat 路由也在後面。**手工維護的清單漂了
兩次**,所以這次不改表,改成把**產生它的指令**寫進去,加每個閘門一句話的判準。

#### 我沒解決的一件事(照實寫)

### 6.16 第十三輪：把掃描跑完（30 個突變，17 killed / 13 survived）

第十二輪的掃描只跑了 44/74。剩下 30 個在**隔離的 worktree** 跑完（前一次和我共用一棵樹，
它的還原吃過我的修改、我的還原也害它一個結果作廢——那是流程錯，不是它的錯）。

**最嚴重的 survivor 是 `PUT /members` 的動詞。** 規則本身是對的（`change_permission`），但

carrier，也是當初讓我發現另外兩個的那個反例）；以及 `_record_usage` 的 cap-skip——「沒有人被
設上限就不寫帳本」這條規則有**兩個寫入者**，而測試只釘住了 PUT 那個，DELETE 那個從來沒有。

**兩個確認是死碼,刪掉:** `turn_gate` 的 `viewer is not None`（`exc.owner` 型別上就是 `str`）
與 `if h.item_id in titles`（`_titles_of` 每個分支都會給值,所以這個過濾器只在「全部丟掉」那
一種情況下起作用——正好和它上面那段文件說的規則相反）。刪掉之後把 `titles[...]` 改成
`.get(..., "")`,避免用 KeyError 換掉原本的靜默丟棄。

**一個 survivor 的結論是「它已經幾乎不可達」**：`_person_disk_gate` 的 `if not owner`。
R7-1 給 `debtor_of` 加上 `created_by` floor 之後，空的 `owner` 會解析到建立者，所以要走到這
一行只剩「那次 store 讀取失敗」——而那條路徑在 `tests/apps/test_resolve.py` 有單元測試。
保留為最後一道安全帶,但在程式碼裡寫明它是安全帶,不要看起來像一般情況。

#### 這一輪我自己的三個錯，都被突變探針抓到

1. **錨點抓錯路由**：我以為在突變 resize 的 slug 檢查,實際打到 `/members` 的。
2. **patch 打不到目標**：`_titles_of` 用函式內 import,我 patch 模組層的 `groups_of` 完全沒生效
   ——那條測試有一半是裝飾品。真因是同一個東西有兩個 import carrier,拿掉多餘的那個之後才對。
3. **reader 用錯**：`total_for` 是加總,刪檔後恆為 0,所以看不到多寫的那一列；要用
   `_per_item_sync`。而且我還把 list 拿去和 `0` 比。

三個都是「測試因為錯的理由而綠」。**探針的價值不在它找到多少缺陷,在它逼我證明每一條斷言
真的看得到它宣稱的東西。**

### 6.17 合併 #777(delete item cascade)：兩個分支替同一個請求寫了不同答案

推上去之後 CI **完全沒有排程**——不是紅,是沒有 check。真因是 PR 變成 `CONFLICTING`,而
GitHub 會安靜地不排程 workflow(memory 裡本來就有這條,我的 watcher 分得出「還沒排程」和
「跑完」,卻分不出「永遠不會排程」)。master 併入了 **#777 delete item cascade**,也就是
issue #711——正好和這條分支同一塊語意。

文字衝突只有一行 import,但行為衝突是真的:

> `DELETE /me/resources/live/{id}` 對一個**已經被 cascade 刪掉**的 item,
> #777 斷言 **404**,而這條分支斷言 **204**。

兩邊都寫了理由,而且**理由並不衝突**:#777 要的是「告訴他已經不在,不要丟 500」;這條分支要的
是「重複按、過期頁面按下去不能像壞掉」(前端那個 mutation 沒有錯誤分支)。**204 同時滿足兩者,
404 只滿足一個**——404 會讓按鈕看起來沒反應,正是雙方都想避免的結果。

所以答案選 204,並把 #777 那條斷言連同理由改寫,而不是讓「誰後合併誰贏」決定。順帶記下我在
這裡又犯的同一個錯:我第一次把判準寫成「解析不到債務人就 404」,但 cascade 是**軟刪除**,
記錄還在、`include_deleted=True` 找得到,所以那個判準根本觸發不到。**判準要放在「還有沒有
環境」上,不是「解不解析得到 item」上**——我又一次把規則裝在我當時在看的那個查詢上。

### 6.18 給下一個人的檢查表

0. **每一個修正都先有一條會紅的測試——包含順手的、防禦性的、boy-scout 的那些。**
   驗收整批工作的問法不是「還有沒有缺陷」，是**「把每個守衛刪掉，有沒有測試會紅」**——後者
   直接指出前者沒做到的地方，而且是機械的。
   探針說某個守衛「全裸」，意思就是**那一條沒有走 TDD**：真的先寫紅測試，守衛不可能沒有測試。
   我漏掉的地方精準對應到全裸的地方（`tools_routes` 的 410、`require_item` 的 410、`/tools`
   的讀取天花板），而我當時的藉口都是「這條太小」或「反正測不到」。**「反正測不到」是警訊**：
   要嘛把 seam 做出來讓它測得到，要嘛根本不要加那個守衛。
   補既有測試缺口時，「紅」的定義是**先突變、確認新測試會紅**，不是寫完看它綠。
1. **新欄位長在共用的 struct 上 ⇒ 先列出所有寫入者**（專屬路由、generic PATCH 的兩種格式、create、import、migrate、job）。
2. **前端 disable ≠ 伺服端拒絕。**
3. **替身要送真實形狀**——specstar 傳 list 不傳 `JsonPatch`；`kind: local` 的 `effective_limits` 原樣回傳而不是 `None`。
4. **一寫就綠的測試要跑突變**，殺不掉就刪掉它，別留著假裝有守衛。
5. **「跟 X 一樣」這句話要指向同一個變數，不是同一個數字。** 我寫「跟 admission 閘門同一個
   視窗」然後硬寫了一個 240 倍差的常數。要嘛傳進來共用，要嘛不要寫那句話。
6. **修正也要 review。** 八輪裡有六輪，最嚴重的發現都是**上一輪修正本身**的缺陷——一個屬性名
   打錯、一個編出來的常數、一個自己開的新門、一個把額度整個架空的 `None`、一個把已刪除 item
   重新打開的預設值、一個把活著的 item 說成「結束了」的手刻副本。換掉機制的修法是新程式碼，
   就要當新程式碼驗。
7. **修完一個形狀，要 grep 全 repo 找同形狀。** 我修掉一個 N+1，一輪之後在隔壁檔案親手
   造了一個一樣的。修完問一句：「同樣的寫法還出現在哪裡？」
8. **改一個 seam 的回傳語意，先數誰在讀那個回傳值**——尤其是把「沒有」當成一種答案的那些。
   `find_work_item` 回 `None` 有兩種意思（沒有這個 item／解析不出來），四個閘門讀成同一種，
   額度就這樣被架空了。合併兩個值之前先問：**有誰會分不出來，分不出來會怎樣？**
9. **自己 docstring 裡寫的「呼叫端自己會擋」，要寫一條測試去按它。** 第六輪那個反方向的錯，
   就是這樣才抓到的——那句話當時是假的。
10. **改一個 seam 之前，先跑一次 grep 找「同一件事的閘門有幾個」。** 這個 repo 的 item 路由前面
    有三個：`item_authz.require_item_access`、`locator.require_item`、`locator.require_access`。
    我裝了兩個。判準要收成一個共用函式，讓「漏掉一個」變成不可能，而不是靠記得。
11. **改到既有行為時，讓那一輪的 CI 跑完再往下走。** 六輪 review 沒抓到的 404/410 契約，CI
    第一輪就紅了——review 找沒人寫過測試的缺陷，CI 守已經寫下來的承諾，兩者不能互相代替。
12. **「某個值等於空」和「查不到這個值」不可以是同一個表示法。** 這份 PR 兩個最嚴重的缺陷是同
    一句話的兩個實例：`owner=""`（清空）和 `find_work_item -> None`（查不到）都被讀成「沒有
    債務人」。要嘛給空值一個 floor（這裡是 `created_by`），要嘛讓兩種情況在型別上分得開。
13. **「收成共用函式」不是寫出那個函式，是每個閘門都真的呼叫它。** 我上一輪寫了
    `refuse_if_gone`，這一輪在唯一沒有授權的那個閘門手刻了第二份，而且它問錯問題。寫完共用
    函式要立刻 `grep` 它的呼叫點數量，對得上閘門數量才算完成。
14. **`if x:` 不等於「x 有說出東西」。** 字串的 falsy 只有 `""`，一個空格就是 truthy。凡是
    「沒填就用預設」的判斷，寫的是 `.strip()` 還是 truthiness，差一個攻擊路徑。
15. **一條規則裝在多個閘門時，測試要走「每個閘門各自獨有的路由」。** `require_item` 的 410
    我改了兩輪都沒測到，因為我的測試全部走另外兩個閘門的路由。突變探針說「刪掉這行沒有任何
    測試會紅」的時候，那不是探針壞了，是真的沒人守。
16. **同一個問題在兩個介面上必須是同一條規則。** 「你看不到但你在付錢的那一列要不要顯示」，
    資源頁和 507 拒絕訊息各自在 docstring 裡寫了相反的答案，兩邊都言之成理。並存＝其中一條
    遲早變成假的。發現兩條就當場合併，不要留著。
17. **判準用哪個形式判斷，就存哪個形式。** `if item.owner.strip(): return item.owner` ——
    判斷用 strip 過的、回傳原值，於是 `"alice "` 記在一個不存在的人頭上，而 UI 每一處都顯示
    「alice」。同一個值有兩種正規化，就是兩條規則。
18. **省下一次讀取的說法要去查那個「一樣」的東西。** 我寫「`require_access` 也付一樣的兩次
    讀取」來合理化多出來的 `get_meta` ——它其實有 5 秒快取，窗內付零，而輪詢路由每次都走。
    §6.13-5 的同一條，這次栽在「快取」這個沒被說出口的差異上。
19. **要跳過一個檢查，就讓「跳過」是型別擋得住的東西。** `slug: str | None` 讓
    `slug_of()` 的回傳值漏傳進來就靜默關掉 #95。換成專屬的 sentinel 型別，同樣的錯就變成
    `ty` 的紅字。**能被機械擋下的規則，不要留給記性。**
20. **天花板要貼著實測值。** 我先寫 `db <= 7`，而要防的回歸正是 6→7 ——留 slack 的天花板
    會眼睜睜看著回歸發生而不出聲。先量，再把界線放在量到的那個數字上。
21. **「哪條路由走哪個閘門」要 grep 出來寫進程式碼，不要憑記憶宣稱。** 我三次憑記憶說錯，
    三次都寫進了註解或 commit message。這種表屬於程式碼（`item_authz.py` 的 module docstring），
    不屬於我的腦袋。
22. **一條規則的測試會不會紅，取決於它有幾個 carrier。** 同一條規則寫在兩個地方，突變任一邊
    另一邊都不會紅——這正是「146 個測試守不住」的機制。**先數 carrier，再決定要幾條測試，或者
    把 carrier 收成一個。**
23. **突變下的斷言要各自獨立。** 我那條測試在突變時第一個請求就丟例外，後兩個斷言沒跑到，
    而我報告「驗過會紅」。三個閘門各自取狀態、最後比對整個 dict，才看得到全部。
24. **一條規則有兩個 carrier 時，兩個都要有。** `_access` 無上限而 `_item_facts` 有上限，
    差別就寫在隔壁檔案的註解裡。補的時候順手問「還有第三個嗎」——`_groups` 就是那樣找到的。
25. **測試的名字不是證據。** 兩條以守衛命名的測試，刪掉守衛照樣綠。要斷言**那個守衛買到的
    東西**（這裡是「不該去查帳本」），不是它順帶不會發生的事。
26. **flaky 在突變掃描裡會製造不存在的覆蓋率。** 它把「沒測到」變成「有測到」，方向正好是
    藏起發現。掃描前先修 flaky，或至少單一紅燈一律重跑再計分。
27. **不懂的測試不要交。** 我寫了一條前端測試,它以我無法解釋的方式失敗;我移除它並把缺口
    寫下來,而不是調到綠。一條我不理解為什麼會綠的測試，明天就會變成一條假裝在守的測試。
28. **會改檔案的 agent 要跑在自己的 worktree。** 我讓一個逐一刪守衛的 reviewer 跑在我正在
    編輯的樹上，它的還原會靜默吃掉我的修改，我的還原也害它一個結果作廢。`isolation:
    "worktree"` 是機械解法。
29. **等背景長跑要看驅動程序還在不在，不是只看標記檔。** `until grep DONE` 在驅動被砍之後
    會永遠空轉，而且被砍和還在跑長得一模一樣。
30. **一條規則有兩個「寫入者」時，測試通常只釘住其中一個。** 「沒設上限就不寫帳本」在 PUT
    上有測試、在 DELETE 上沒有，而兩邊各有一份規則。先數寫入者，再數測試。
31. **突變探針自己出錯的次數,和它找到的缺陷一樣有價值。** 這一輪我三次讓測試「因為錯的理由
    而綠」：錨點打到別條路由、patch 打不到函式內 import、reader 看的是加總而不是那一列。
    探針的價值是逼我證明每一條斷言真的看得到它宣稱的東西。
32. **PR 沒有 checks，先查 `mergeable`。** `CONFLICTING` 會讓 workflow 安靜地不排程；
    等待迴圈要能分辨「還沒排程」「不會排程」「跑完」三種狀態，否則你會盯著一個永遠不來的
    綠燈。
33. **合併衝突要比對「理由」而不是「斷言」。** 兩個分支對同一個請求寫了不同答案時，先把雙方
    註解裡的理由列出來——這次其中一個答案同時滿足兩邊的理由，另一個只滿足一邊，選擇就不是
    偏好問題了。
34. **`ty` / `tsc` 是第三種視角**：這次它們抓到六個沒有任何測試會注意到的東西（一個 union 回傳把 `memory_bytes` 拓成 `int|float` 交給 cgroup、`**kwargs` 讓型別檢查失效、五處前端接線缺口）。
