# 撞到步數上限不該終止一個 goal(#721)

## 症狀

一個設了 goal 的聊天,畫面上同時出現三件互相矛盾的事:

- 對話裡一則橫幅寫著**「已達回合上限(30)」**
- goal 面板顯示 **0/3 輪**
- 對話停住,沒有自動續跑

三個都是對的,而且講的是同一件事:**第 1 個 turn 撞牆,而撞牆被當成失敗。**

## 三個計數器,不是一個

這是理解整件事的前提。名字都叫「回合/輪」,但它們是三個獨立的東西:

| 設定 | 是什麼 | 預設 |
|---|---|---|
| `runner.max_turns` | **一個 turn 之內** agent 最多走幾步(呼叫工具、再想、再呼叫) | 10 |
| `goal.max_rounds` | 上班時間,goal 自動續跑幾個 **turn** | 3 |
| `goal.offhours.max_rounds` | 下班時間,跨**所有夜晚**的累計 turn 數 | 30 |

⚠️ **回報這個問題的部署把 `runner.max_turns` 調成了 30,而 offhours 預設也是 30。**
兩個 30 撞在一起,讓症狀看起來像「下班預算用完了」——但那個部署根本沒設下班窗。
排查時第一件事是確認畫面上那個數字來自哪一個。

橫幅的字來自 `banner.maxTurns`,由 `max_turns_exceeded` 事件驅動,也就是
`runner.max_turns`。goal driver 有自己的一套字(「額度用盡,還沒完成」),看到那句才是
goal 的預算真的用完。

## 根因

`_goal_followup` 把所有非 `ok` 的結束歸成同一種失敗,而上班時間的規則是「失敗就交還給人」
(#613)——理由很正當:有人坐在那裡,把壞掉的東西交回去比自己亂試好。

但「**還沒做完**」和「**做錯了**」意義相反:

- 工具報錯 = 這一輪走錯了 → 交還給人是對的
- 步數用完 = 這一輪**沒走完** → 這正是「續跑」存在的理由

collapse 成同一種之後,goal 的預算變成**永遠花不掉**:第一輪撞牆就交還,`rounds_used`
停在 0。

## 修法

新增一個判斷,並在**三個**判斷點使用它:

```python
def _ran_out_of_steps(outcome: str) -> bool:
    return outcome == "max_turns"
```

| 判斷點 | 原本 | 改成 |
|---|---|---|
| 交還閘門 | `if outcome != "ok" and not unattended: return` | 步數用完放行 |
| goal 檢查 | `met = outcome == "ok" and check_goal_met(...)` | 步數用完也要判斷(它產生了證據) |
| stall gate | `no_progress = outcome != "ok" or 指紋相同` | 步數用完**不算**沒進展 |

⚠️ **三個都要改。** 漏掉任何一個,修法只會生效一半——只改交還閘門的話,續跑會發生但
第二輪就被 stall gate 判定卡住;只改 stall gate 的話,根本走不到那裡。

### 為什麼 stall gate 可以放寬

那道閘門是為了攔「agent 在原地繞」。它本來就有一個**真正在偵測繞圈**的判準:
`turn_signature`——上一輪工具呼叫的指紋,連續兩次一模一樣就判定卡住。

`outcome != "ok"` 只是那個判準的**粗糙代理**,而且方向是錯的:一個跑很久的大問題會不斷
撞上限,卻每次都在做不同的事。放寬之後,剎車仍在(指紋),而且是更準的那個。

⚠️ 代價:**一個每輪換不同工具、但其實沒有進展的 agent,會把預算跑完才停。**
上班 3 × 30 = 90 步;下班 30 × 30 = 900 步的無人看管花費。指紋抓不到那種。

### 定案的取捨

| | |
|---|---|
| 被吸收的那一輪 | **要扣**。它是真的跑過的 turn;不扣就沒有天花板 |
| 下班時間 | **一樣**。照時鐘分岔的規則沒有人預測得準,而且「大問題要跑久」在沒人看著時更成立 |
| goal 已達成 | 不續(照舊,標記達成)。步數用完不代表沒做完——可能做完了、只是來不及說 |
| 檢查器故障 | 不續、交還給人。未知要往「已知安全」的那邊倒 |

## 刻意不做:把橫幅藏起來

**使用者仍會看到「已達回合上限(30)」,然後對話自己動起來。** 那個誤導留著,是知情的決定。

三種藏法都評估過:

1. **只有資料庫不寫,事件照送** — 正在看的人還是看得到,重新整理才乾淨。**一半的效果。**
2. **兩邊都不出現** — `max_turns_exceeded` 是 **terminal 事件**,前端拿它**關閉串流**和
   **解鎖輸入框**。拿掉會讓輸入框在續跑沒來時鎖死,得另外補一個替代事件。
3. **寫了再刪** — ⚠️ **實測做不到**。前端在 turn 結束後會重讀對話,但用的是 `reconcile`,
   而它的契約明寫「絕不移除」(否則會抹掉剛串流進來的回覆)。後端刪乾淨,螢幕上那個
   橫幅還在。

第 3 種特別值得記下來,因為它**看起來**最直覺,而失敗的地方在前端一個共用契約裡——
不去讀 `useChatLog.reconcile` 就不會發現。

把橫幅講清楚是一個獨立的、純前端的小改動,值得另開一張票。綁在一起會讓「行為修正」被
「畫面呈現」的討論拖住——這次就發生了。

## 一個新暴露面

改動之前,撞上限**根本不會呼叫 goal 檢查器**(那行 `outcome == "ok"` 擋著);改完之後會。
所以檢查器端點的故障在這條路徑上**變得可達**。

`_goal_followup` 原本的 `except` 只接 `ResourceIDNotFoundError` / `ResourceIsDeletedError`,
LLM 例外會逸出到一個 detached task——結果是「不續跑」(符合定案),但只會在 log 留下
`Task exception was never retrieved`,沒有任何東西說明原因。已補上一個 `except` 讓它安靜
且明確。

## 驗收

`tests/api/test_goal_max_turns.py`:

- 撞上限 + 未達成 → `rounds_used` 0→1,且真的送出下一輪
- 撞上限 + 已達成 → 不續,標記達成,`rounds_used` 仍為 0
- 檢查器丟例外 → 不續、goal 留 `active`,且不炸掉 detached task
- 連兩輪撞上限、工具呼叫**不同** → 跑滿預算後 `exhausted`(不被誤判為卡住)
- 連兩輪撞上限、工具呼叫**相同** → 判定 `stalled`(剎車仍在)

前兩條與最後一條各自做過突變驗證:拿掉指紋偵測 → 剎車測試變紅;不改 stall gate →
誤判測試變紅。
