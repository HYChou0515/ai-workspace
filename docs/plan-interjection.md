# 插話：AI 還在跑的時候送出的訊息，要真的有插話的效果

**狀態:** grill 完成(2026-10-16,master `203b0e38`,Q1–Q10);P1–P6 施工於 #969。施工時定的事與和上文不同的地方在 §9 —— §9 優先於上文。
**來源標記:** 〔user〕= user 的原話或明確選擇;〔查證〕= 讀程式碼確認的事實;〔建議〕= 我提的、user 未明確表態;〔施工〕= 施工時我定的,user 還沒看過。

## 1. 問題〔user〕

「在上輪對話還沒跑完的時候插嘴,加上 step limit 150,對話者會覺得 AI 雞同鴨講。」
「我自己插自己話時,他不會回答我第二個問題;我在第一個問題回答完後再問第三個問題,他會開始回答我第二個問題。」
「我希望插話是真的能有插話的效果,否則很容易看起來降智。」

## 2. 為什麼現在會雞同鴨講〔查證〕

1. **插話那一輪的上下文在插話當下就定住了。** `chat_send._start_turn` 在接受訊息時就建 ctx
   (`preparing` → `build_chat_turn(history_messages=_history_before(conv.messages, created, …))`),
   之後才 `enqueue`。Q2 被接受時對話裡只有 `[Q1, Q2]`,所以 T2 的歷史只有 `[Q1]` —— T1 的
   工作與回答永遠不會進 T2。KB 聊天一樣(`kb_chat_routes`:`history_items(chat.messages[:-1])`)。
2. **模型先回沒人回的那一題。** T2 看到的是 `user: Q1` + `user: Q2`,Q1 沒有回答,模型通常
   先回 Q1;下一輪 Q3 看到 `Q1, Q2, A1, A2(又是 Q1)`,Q2 沒有回答,於是回 Q2。每輪落後一題。
3. **步數上限的提示不進歷史。** `turns.history_items` 把 `role="error"` 全濾掉,只有
   `cancelled` 折成一句標記(#199);`max_turns` 被濾掉,所以下一輪不知道上一輪是做到一半被切。
4. **存檔順序是 Q1, Q2, A1, A2。** 問題在接受時存(202 的規則),回答整輪結束後才接在最後。

## 4. 機制

### 4.1 佇列裡的一則訊息〔建議〕

`ChatTurnEngine` 的佇列項目(`_QueueItem`)改成一個 dataclass `_QueueEntry`,多帶三樣東西:

- `author` 與 `message_at`:這則訊息是誰、在對話裡的 `created_at`。吸收與合併都靠它認人、認位置。
- `refresh`:surface 給的函式,engine 在這則訊息**開跑之前**呼叫,讓 surface 重讀對話、
  重算 `ctx.history`。只有「排在別的輪後面」的訊息會被呼叫(`waited`,enqueue 當下有輪在跑或
  佇列不空);一送就跑的訊息不重讀,行為與今天一位元不差。
- `on_absorbed`:這則訊息被別的輪負責回答時呼叫(app 聊天用它結束自己的 turn-claim;KB 沒有 claim)。

另有 `absorbed` 旗標:被吸收或合併的項目留在 `asyncio.Queue` 裡,worker 取到時直接跳過
(它的 future 由負責的那一輪結束時解掉)。

**多 pod 的範圍〔查證〕:** 同一個對話的佇列本來就是 pod 內的(`_WorkspaceSession`),
靠 sticky 路由把同一對話的送出送到同一顆 pod;吸收與 Q2 的停止都在這個佇列上做,所以範圍
和今天的排隊一樣。插話落在另一顆 pod 時,它在那顆 pod 自己排隊(今天就是這樣),不會被吸收。

### 4.2 合併沒被看過的排隊訊息(Q10、Q1 的邊界)〔建議〕

worker 取到一則還沒被看過的項目時,把佇列裡**此刻所有**還沒被看過、也沒在準備中被停止的
項目一起取出:**最後一則**當主訊息(它的 ctx = 這一輪的身分與設定),前面幾則依序成為這一輪的
「開頭插話」—— 以使用者訊息放在歷史之後、主訊息之前。歷史由 `refresh` 從**第一則**之前重算。

用最後一則的身分,是 Q2 推出來的:佇列裡混了兩個人時,後面那個人必然是用 Q2 停掉前一輪的人,
接手的就該是他。

### 4.3 吸收(Q1、Q4、Q7)〔建議〕

- ctx 新增 `take_interjections`:engine 在一輪開跑時掛上,呼叫時取出佇列裡**同一個作者**、
  還沒被看過的項目,標成 absorbed,回傳 `Interjection`(內容含 skill/標記前綴、圖片 data URL、
  作者、`message_at`、套用的 skill)。
- runner 在 SDK 的 `RunConfig.call_model_input_filter` 裡呼叫它(每次呼叫模型之前都會經過;
  拿得到「到目前為止的完整輸入」)。有插話時拋 `_Interjected(輸入 + 插話的 user 項目)`;SDK 原樣
  往外傳(`run_internal/turn_preparation.py:maybe_filter_model_input` 的 `raise`)〔查證〕。
- `run()` 接到 `_Interjected`:每則插話吐一個 `Interjected(author, created_at)` 事件,然後用那份
  輸入開**新的一段** `Runner.run_streamed`,`max_turns` 從頭算(Q4)。這不是重試:不算 attempt。
- 吸收時把該輪的 `kb_search_budget` / `wiki_search_budget` / `kb_grep_budget` 重算滿,把插話的
  `apply_skills` 併進來(Q7)。推理強度與揭露開關不動。
- 正在跑的工具不中斷:filter 只在下一次呼叫模型前跑(Q6)。

### 4.4 存檔順序(Q3)〔建議〕

reducer 收到 `Interjected` 時在 `produced` 裡放一個位置標記(`role="interjection"`,帶
`message_at` 與作者),並讓下一段文字開新的 assistant 訊息。存檔用一個共用的純函式
`splice_turn`:把已經存在的那則插話**移到**標記的位置,其餘照順序接上。兩個 surface 的 persist
都用它。插話仍在接受時存好,所以 202 的規則不變。

### 4.5 別人插話(Q2)〔建議〕

`enqueue` 收到的作者若和正在跑那一輪的作者不同,engine 停掉那一輪(只停正在跑的那一輪,不碰
任何人還在準備中的送出),記下是誰打斷的。被停那一輪的結尾是 `error_kind="interrupted"`、
`author` = 打斷的人。歷史把它折成一句「上一輪被 X 的新訊息打斷」,畫面顯示「已被 X 的訊息中斷」。
目標自動推進的輪:作者是設定目標的人,所以設定者插話是同一個作者(吸收),別人插話就停(Q8)。

### 4.6 步數上限的標記(Q5)〔建議〕

`history_items` 對 `error_kind="max_turns"` 比照 `cancelled`,把一句「(上一輪在完成前因步數上限
停止,以上是做到一半的結果)」折進前一則 assistant。只說事實,不叫它做什麼。

### 4.7 畫面(Q7、Q9)〔建議〕

- `Interjected` 事件(`api/events.py` + `web/src/events.ts`):前端把那則插話泡泡移到串流目前的位置,
  之後的文字畫成新的回答。泡泡下的狀態:送出後「AI 做完目前這一步後會回覆」;收到 `Interjected`
  「AI 已看到,會一併回覆」;它在等的那一輪結束時還沒被吸收「這一輪結束後會接著回答」。
- 自己的輪在跑時,輸入框顯示推理強度與揭露開關「這一輪開始時已決定」。
- 持久化的 `interrupted` 結尾顯示「已被 X 的訊息中斷」。

## 5. 不做的事

- 插話不中斷正在跑的工具(Q6)。
- 跨 pod 吸收:同一對話的佇列本來就在一顆 pod 上(§4.1)。
- workflow(Q8)。
- 不新增訊息欄位、不 bump schema:位置靠移動既有訊息,打斷者放在 error 訊息既有的 `author`。

## 6. 對既有規則的影響

CLAUDE.md「Chat turns run through one `ChatTurnEngine`」那段說 Q1, Q2, A1, A2 是刻意的、「要改
必須先有 turn id」。理由是 render 時去猜「第 N 個回答屬於第 N 個問題」會出錯。本計畫不猜:
插話的位置由 reducer 在它**被看到的那一刻**記下,存檔時把那則訊息移過去 —— 位置是被量到的,
不是推出來的。排隊(沒被吸收)的訊息仍是 Q1, Q2, A1, A2+Q2 的順序,而那一輪會一起回答它們(Q10)。
同一個 PR 更新那段。

## 9. 施工時定的事

- **C1〔施工〕排隊的訊息也照「被讀到的位置」存,不只吸收的(推翻 §6 原本「排隊的維持 Q1, Q2, A1, A2」)。**
  P1 的第一版用「Q2 之前的對話」重算歷史,紅燈抓到:Q2 存在 A1 **之前**(接受時就存),所以
  「Q2 之前」正好不含 A1。正確的歷史是「整條對話扣掉這一輪要回答的訊息」(`thread_without`),
  那幾則放在歷史之後。存檔也一樣:這一輪的產出以 `PLACE_ROLE` 標記開頭,persist 把那幾則訊息
  移到標記的位置,對話讀成 Q1, A1, Q2, A2 —— 和 AI 讀到的順序一樣,也和即時畫面一樣(插話泡泡
  本來就畫在 A1 下面)。用的是 Q3 同一套機制,不是第二套規則。
- **C2〔施工〕合併與吸收只套用在帶有聊天訊息身分(`QueuedMessage`)的項目。** workflow 也走同一個
  `enqueue`,每一步必須各自一輪;沒帶訊息身分的項目照舊一則一輪。
- **C3〔施工〕補跑(`rerun`,plan-graceful-shutdown P3)也在開跑時重組並移位置。** 補跑的 pod 佇列是空的,
  看不出那則訊息曾經排隊,但對話裡它可能在它等的那個回答上方 —— 同一個 bug 的另一個入口,測試
  `test_a_rerun_of_a_queued_question_is_handed_the_answer_it_waited_for`。(第一版用 `QueuedMessage.rebuild`
  旗標,會把 #624 提示移到問題前面;C8 起每一輪都重組、只在需要時才移,旗標拿掉,提示的位置回到 master 原樣。)
- **C4〔施工〕被合併的訊息,它的 claim 在負責那一輪的回覆「確定是這顆 pod 的」並存好之後才結束**
  (`_settling`)。被交接出去的那一輪沒寫任何東西,它合併的訊息仍然欠著,留給接手的 pod。
- **C5〔施工〕sub-agent 不繼承插話的讀取。** `_child_context` 是 `dataclasses.replace`,沒點名的欄位
  都跟父 ctx 共用;不清掉的話,sub-agent 的模型呼叫會把插話讀走,而父那一輪不會放、也不會回答它。
  `take_interjections` / `leading_interjections` / `history_builder` 在子 ctx 一律清空。
- **C6〔施工〕非串流路徑(`WORKSPACE_AGENT_STREAM=0`)被插話切斷時,補發那一段做過的工具與文字。**
  `Runner.run` 跑完才交出 items,被 `_Interjected` 打斷就什麼都沒交;那一段的東西只存在「下一次
  呼叫原本要送出的輸入」裡,從那裡補發(`_segment_events`),不然那段跑過的工具在畫面與存檔都消失。
- **C7〔施工〕插話只在下一次「呼叫模型之前」被讀。** 模型已經在寫最終回答(不會再呼叫模型)時到的
  插話,這一輪讀不到,它照 P1 排隊、合併、在下一輪開跑時讀 —— Q1 的邊界情況就是這條路。

第一輪對抗式 review(conformance / defect / regression)找到的,修法如下(C8–C12):

- **C8〔施工〕重組歷史時扣掉「所有還沒被回答的訊息」,而且每一輪都重組。** 第一版只扣這一輪要回答的,另一則
  已存好但還在準備中的訊息(壓縮、喚醒沙盒…)就漏進別人的歷史,而且位置錯(F1/R3);要不要重組又是在進佇列時
  決定,準備期間別輪跑完就沒重組。現在「還沒被回答」由結構算:準備中(`PendingTurn.at`)、在佇列裡、這一輪要
  回答的;App 聊天再加上 claim 帳本上還欠回覆的(別的 pod 上的)。`refresh` 回傳要不要移位置(`must_move`:
  後面有它沒看過的東西才移;為這一輪寫的 #624 提示、摘要不算)。`waited` / `rebuild` 兩個旗標拿掉。
- **C9〔施工,請 user 確認〕被停掉的那一輪(按停止,或被別人接手)不算回答了它讀到的訊息。** 它們回到佇列最前面,
  claim 不結,由下一輪回答(R2)。理由:以前按停止不影響排隊中的訊息,吸收之後卻會把讀到的一起殺掉 —— 畫面剛說
  「AI 已看到,會一併回覆」,結果沒有回覆。這等於把 Q10 細修成「第一個**沒被停掉**、看得到它的那一輪負責回答」。
  前端:被停掉時「AI 已看到」改成「這一輪結束後會接著回答」。
- **C10〔施工〕目標自動推進的那一輪不是人在說話**(`QueuedMessage.driven`):不接手別人、不被讀進別人的那一輪、
  不和人的訊息合併,照舊排隊(R1)。準備中已被停止的訊息也不接手(R4)。Q8 的「設定者插話吸收、別人插話接手」
  照舊。
- **C11〔施工〕取消延後一個 event loop tick。** 一輪的 task 建好、還沒跑第一步時被取消,它的本體不會執行,連結尾都
  不寫(F3)。接手與停止都改成 `call_soon(turn.cancel)`;停止在 master 上就有同樣的窗口,一併修。還在準備(重組
  歷史)時被接手,就把整組訊息放回佇列,由接手者那一輪一起回答。
- **C12〔施工〕插話後續跑的輸入 = 目前的歷史 + 之後的內容,每次送出時才組。** 第一版存的是整份輸入的快照,#624
  的超量恢復縮的是 `ctx.history`,送出去的卻沒變,同一個請求重送到放棄(F2)。
- 其他:合併訊息套用的 skill 也併進來;一輪的 `accepted_ms` 取它回答的最早那則;放回位置時比對作者(同一毫秒
  兩人送出)。§4.4 寫的標記名稱 `role="interjection"`,實作是 `PLACE_ROLE = "place"`,帶作者。

第二輪 review(修正驗證 + regression、veracity)找到的(C13–C15):

- **C13〔施工〕pod 收攤時被取消的那一輪不是「停止」。** `aclose` 先取消殘留的那幾輪、再取消 worker,worker 看到的
  只是「這一輪被取消了」,照 C9 把合併的訊息放回佇列、開新的一輪 —— 在要關的 pod 上,`aclose` 結束後還在跑,而
  claim 已經交給別的 pod 補跑。現在 `aclose` 過了期限要取消殘留之前先設旗標:被取消的那一輪照交接處理(不放回、
  叫醒 POST、claim 留給補跑的 pod),worker 也不再開新的一輪。
- **C14〔施工〕「哪一則訊息」一律用(時間、作者)認。** C12 只修了放回位置那一處;`thread_without`、`must_move`、
  「還沒回答的」集合都還是只看時間,同一毫秒兩人送出時會漏掉、留錯。`PendingTurn` 多記 `sender`(它的
  `author` 對目標推進輪是刻意留空的,好讓任何人的停止都碰得到)。
- **C15〔施工〕KB 送出也走 `preparing()`**(C8 要知道哪些 KB 訊息還在準備中)。兩個附帶的行為改變:KB 的送出在
  準備中被按停止,那個問題會被取消(寫「已取消」結尾,和 App 聊天一樣;以前照跑);pod 收攤時還在準備的 KB 送出
  會留下「已取消」結尾(KB 沒有 claim,本來就沒有別的 pod 補跑;以前是沒有任何結尾)。成本:每一輪開跑多一次
  對話讀取,App 聊天再多一次 open claim 列表(全表,但只有正在進行的輪數那麼多列)。
- **C16〔施工〕veracity 找到的:** 讀進來的插話留下的位置標記也帶作者(C14 只修了開頭那幾個);目標推進輪
  「不被合併、不被讀進設定者那一輪」、準備中被停止的送出「不在佇列頭也不被合併」、合併訊息的 skill、
  `accepted_ms` 取最早、「沒人插話仍在 `max_turns` 停下」都補了會紅的測試。KB 沒有 claim,所以「還沒回答的訊息」
  在 KB 只認得同一顆 pod 上的(文件寫明)。輸入框那句改成「做完這一步後會讀到;已經在寫最後回答就由下一輪接著
  回答」(C7)。§4.1 描述的 `absorbed` 旗標與留在 `asyncio.Queue` 的做法沒有實作:實作是看得到內容的 `_TurnQueue`,
  被讀走或合併的項目直接從佇列取出(`take`),由負責那一輪結算或放回(C9、C13)。
