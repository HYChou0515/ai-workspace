# 長對話收起中間

**問題**：很長的對話開不起來。兩個聊天面板（App 的 `AgentPanel`、知識庫的
`KbChatPanel`）都把整串 `log.entries` 一列一列畫進 DOM。#1002 量過 300 輪：
打開要排版 1.9s + JS 1.7s、11.4 萬個 DOM 節點；更長的對話就開不起來。

**這份計畫推翻 #1002 的一個決定。** 當時 user 選擇「整串都畫」（瀏覽器 Ctrl+F
要找得到舊訊息），記在 `docs/subsystems/frontend.md` 的設計決策表，不是計畫文件。
這次 user 改成收起中間，該列已改寫。

## 決定

| # | 決定 |
|---|---|
| D1 | 預設只畫**最上面 100 則**和**最新 1000 則**，中間收起來 **[user]**「Keep最上面100和最新1000」。一則 = feed 的一列（`log.entries` 的一項：一句問話、一段回答、一張工具卡）。總數不超過 1100 就全部畫，沒有收起條。 |
| D2 | 收起的地方可以展開，**一次 1000 則**，不是一次全開 **[user]**「也不是全展開 一次開1000」。 |
| D3 | 收起條上有**兩個**按鈕，由人選方向 **[user]**「讓他選 中間省略部分應該要有兩個地方可以點 一個網上一個往下展開」：「↓ 再顯示接下來的 N 則」讓上面那段往下長；「↑ 再顯示更早的 N 則」讓下面那段往上長。N = min(1000, 還收著的則數)。照 GitHub PR 時間軸 / diff 收起區的做法（兩頭各一個展開）。 |
| D4 | 展開時你正在看的那一列不動：往下長時，上面那段的內容留在原位（新的列出現在收起條上方、把條往下推）；往上長時，下面那段的內容留在原位（新的列出現在條下方，捲動位置補上新增的高度）。 |
| D5 | 數量是相對的：上面 = 前 `100 + 往下展開過的` 則，下面 = 最後 `1000 + 往上展開過的` 則。對話進行中新訊息進來，下面那段最舊的一列會併進收起區。（不用「鎖住打開時的索引」：首次載入、斷線重抓、undo 都會整串重建，索引鎖不住。） |
| D6 | 展開狀態只在這次打開時有效：換對話、重新整理就回到 100 / 1000。 |
| D7 | 兩個聊天面板都改，共用同一個 hook（`useCollapsedFeed`）和收起條元件；資料、API 不動，只決定哪些列進 DOM。列的 `key` / `index` 仍是它在整串裡的位置，所以回答問題、undo、回報有誤等以 index 找列的動作照舊。 |

## 不做的

- **虛擬化**：列高不固定（markdown、工具卡、圖片），而且 user 要的是「中間收起來、自己選要不要展開」，不是「看不到的不畫」。
- **後端分頁**：user 說的是「前端不要 render 中間」；整串照樣抓回來（undo、匯出、已回答的問題都讀整串）。

## Phases

- **P1**：`useCollapsedFeed`（純計算 + 展開 + 換對話重置）與收起條，接進兩個面板；D4 的捲動位置。
- **P2**：用 #1002 的量測方式量打開長對話（3000 列）前後差異；文件（`frontend.md` 決策表、migrations）。
