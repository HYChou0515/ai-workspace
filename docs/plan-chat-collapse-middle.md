# 長對話收起中間

**問題**：很長的對話開不起來。兩個聊天面板（App 的 `AgentPanel`、知識庫的
`KbChatPanel`）和底部面板的三個紀錄分頁（Agent log、output、run history）都把整串一列一列畫進 DOM。#1002 量過 300 輪：
打開要排版 1.9s + JS 1.7s、11.4 萬個 DOM 節點；更長的對話就開不起來。

**這份計畫推翻 #1002 的一個決定。** 當時 user 選擇「整串都畫」（瀏覽器 Ctrl+F
要找得到舊訊息），記在 `docs/subsystems/frontend.md` 的設計決策表，不是計畫文件。
這次 user 改成收起中間，該列已改寫。

## 決定

| # | 決定 |
|---|---|
| D1 | 預設只畫**最上面 100 則**和**最新 1000 則**，中間收起來 **[user]**「Keep最上面100和最新1000」。一則 = feed 的一列，也就是 `log.entries` 的一項：問話、回答、工具卡，也包括通知、錯誤、workflow 步驟、摘要這類列（這個讀法是 agent 定的：問 user 數字之前就說明了，user 沒有反對）。工具呼叫多的對話，1000 列可能只是幾十輪。前 100 列的邊界也可能切在一輪中間。總數不超過 1100 就全部畫，沒有收起條。 |
| D2 | 收起的地方可以展開，**一次 1000 則**，不是一次全開 **[user]**「也不是全展開 一次開1000」。 |
| D3 | 收起條上有**兩個**按鈕，由人選方向 **[user]**「讓他選 中間省略部分應該要有兩個地方可以點 一個網上一個往下展開」：「↓ 再顯示接下來的 N 則」讓上面那段往下長；「↑ 再顯示更早的 N 則」讓下面那段往上長。收著的不超過 1000 則時，方向沒有差別，只留一個「顯示其餘 N 則」（GitHub diff 收起區剩得少時也只給一個展開全部）。照 GitHub PR 時間軸 / diff 收起區的做法。 |
| D4 | 往下長時，上面那段留在原位：新的列出現在收起條上方，把條和下面那段往下推。往上長和「顯示其餘」時，下面那段留在原位：新的列出現在條下方，捲動位置補上新增的高度；對話是從最新的地方打開的，往回捲到收起條的人看的是下面那段。 |
| D5 | 數量是相對的：上面 = 前 `100 + 往下展開過的` 則，下面 = 最後 `1000 + 往上展開過的` 則。對話進行中新訊息進來，下面那段最舊的一列會併進收起區。（不用「鎖住打開時的索引」：首次載入、斷線重抓、undo 都會整串重建，索引鎖不住。）例外：全部展開過一次就維持全部展開，新訊息不會讓收起條再冒出來。 |
| D6 | 展開狀態只在這次打開時有效：換對話、重新整理就回到 100 / 1000。 |
| D7 | 兩個聊天面板和底部面板的 Agent log / output / run history 分頁都走同一個元件 `CollapsedFeed`（數量的計算是 `lib/collapsedFeed.ts` 的 `feedWindow`）。底部面板的 output / run history 分頁交給它的是工具呼叫（output 只交有輸出的），所以那兩個分頁算的是工具呼叫，不是列；換分頁就回到預設（D6 的延伸），不記各分頁的展開。資料、API 不動，只決定哪些列進 DOM。列的 `key` / `index` 仍是它在整串裡的位置，所以以 index 找列的重跑、undo、回報有誤照舊；所有列和收起條放在同一個 keyed 陣列，列跨過收起條時不會重新掛載。 |

## 不做的

- **虛擬化**：列高不固定（markdown、工具卡、圖片），而且 user 要的是「中間收起來、自己選要不要展開」，不是「看不到的不畫」。
- **後端分頁**：user 說的是「前端不要 render 中間」；整串照樣抓回來（undo、匯出、已回答的問題都讀整串）。

## Phases

- **P1**：`CollapsedFeed` 元件與 `feedWindow`，接進兩個聊天面板和底部面板的三個分頁；D4 的捲動位置。
- **P2**：用 #1002 的量測方式量打開長對話（3000 則與 20000 則）前後差異；文件（`frontend.md` 決策表、migrations）。
