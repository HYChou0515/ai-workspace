# Plan — a workflow agent's malformed output is repaired, not the step re-run

**Status:** grilled 2026-10-16 on master `d29f0ccb`.

**Markers:** **[user]** = the user's words or explicit choice · **[verified]** = read from
the code at `d29f0ccb` · **[proposal]** = mine, overridable.

## 1. The problem

The user, on a workflow agent step that must answer in JSON **[user]**:

> Workflow agent 輸出必須是json, 但目前好像會讓他整個step重跑 我以為我們只是要他重新輸出？

What happens today **[verified]**:

- An agent step's reply is parsed with a plain `json.loads` (`workflow/steps.py:52`,
  `_parse_fields`) and checked against its `outputs` (`workflow/dsl.py:452`,
  `_outputs_check`). An `out` step with `kind: json/yaml/csv` is parsed by
  `artifact_valid` (`workflow/checks.py:77`).
- A failed check makes `run_step` (`workflow/engine.py:113`) call the step's `execute`
  again. For an agent step that is `drive_turn(_retry_prompt(prompt, feedback), tools)`
  (`steps.py:63`, `:160`): a brand-new turn with the **whole original prompt** plus one
  sentence of feedback, and **every tool the step holds**. Nothing stops it redoing its
  tool calls, and a model handed the whole task again commonly does — slow and paid for
  again (that part is model behaviour, not read from the code).
- DSL `retries` defaults to 2 (`dsl.py:141`), so a format slip can cost three full runs
  of the step.
- The failed reply does reach the next attempt's history (`api/workflow_exec.py`
  `persist` appends what a turn produced; the next turn reads `conv.messages`), but a
  node's own prompt is never stored (`workflow_exec.py:304`), so the history shows an
  answer with no question, and the retry then sends the question again in full.
- Two more facts shape the fix:
  - A `map`'s elements run on their own lanes (`handle.py:243`, `sub_handle`) but
    persist into the **same** workflow chat. With elements in parallel, the reply just
    above in the history may be another element's.
  - Nothing tells the model the shape it must answer in. `outputs` checks the reply
    afterwards (`dsl.py:452`) and feeds a `map`'s fan-in, but is never put into the
    prompt: the author's prompt is all the model sees (`dsl.py:341` says the author has to
    write the shape there).

## 2. Decisions

| # | Decision |
|---|---|
| D1 | A reply whose **format** fails is repaired in place: one more turn on the same chat whose only request is to re-emit the answer, **with no tools**. The request says to reply with **JSON only** — no preamble, no explanation, no code fence **[user]** 「讓他不要說一些有的沒的 只有json」. |
| D2 | When the repair attempts run out, the step **fails** with the last reason. It does not fall back to re-running the step **[user]** 「B」. |
| D3 | The repair request (a) says the reply is still not valid JSON / does not match the required format, (b) quotes the faulty part, and (c) gives an example built from `outputs` **[user]** 「系統回話時要告訴他 他仍然輸出了非json, 指出他的錯誤片段，再附上範例」. |
| D4 | `retries` now counts repair attempts, default 2. No switch keeps the old behaviour **[user]** 「好」. |
| D5 | Only failures of the reply's **own format** are repaired: `outputs` (not JSON, missing field, wrong type, value outside its enum) and an `out` step's `kind: json/yaml/csv` failing to parse. `requires`, `produces` and an author-written `check` keep re-running the step with feedback, as today **[user]** 「可以」. |
| D6 | Repairs and re-runs share one budget, `retries`: a step spends at most `retries` extra attempts of either kind **[user]** 「Ok」. |
| D7 | The run log shows a repair as 「修正輸出格式（第 n 次）」 with its reason, apart from 「重試中」 **[user]** 「要 我們就是希望他能夠好好輸出」. The repair request itself also appears in the workflow chat, so the reader can see what was asked and what came back. |
| D8 | A step with `outputs` gets, at the end of its **first** prompt, a format instruction generated by the system: JSON only, the fields with their types and allowed values, and an example — the same text the repair request uses. An `out` step with `kind: json/yaml/csv` gets "reply with only the <kind> content itself" **[user]** 「好」. |

### Relation to earlier decisions

`plan-workflow-language-alignment.md` D6 says: never sanitize a model's output; when a
check catches pollution, feed the reason back so the model produces clean output itself.
This plan keeps that rule — nothing strips or rewrites a reply. It changes only what is
fed back (a repair request instead of the whole task) and with which tools (none). It
refines that decision rather than overturning it, so the old plan is not marked.

What changes is the spec text that described the old retry: `docs/workflows.md` §6 ("the
failure reason is fed back into a re-run of the same step") and
`docs/workflow-reference-model.md` §2.2 ("reuses `retries` and `_retry_prompt`"). Both
are updated in the same PR.

## 3. Mechanism

### 3.1 Which failures are format failures (D5)

A check says so itself: `CheckResult` gains `format: bool = False` **[proposal]**. The
rule lives where the verdict is made, not in a list of reason strings kept in sync by
hand.

| Check | Sets `format` when |
|---|---|
| `_outputs_check` (`dsl.py`) | every failure: not an object / missing field / wrong type / outside enum |
| `artifact_valid` (`checks.py`) | `kind` json/yaml/csv does not parse (or CSV is not rectangular). Not for a missing file, an empty file, or `requires` |
| `_produces_check`, the author's `check`, `exit_zero`, `file_nonempty`, `choice_in`, `collection_has` | never |

### 3.2 The engine (D2, D4, D6)

`run_step` takes an optional `repair: Callable[[CheckResult], Awaitable[Any]]`. After a
failed verdict, with attempts left:

- `verdict.format` and `repair` given → the next attempt is `await repair(verdict)`, and
  the engine emits `StepRepairing` (§3.6) instead of `StepRetrying`;
- otherwise → `await execute(feedback)`, as today.

Both spend the same loop counter (D6). When the loop ends the step fails with the last
reason (D2). A step with no `repair` (a sandbox step with `outputs`, the plain
`agent_step`) re-runs as before; only its reasons changed (§6: they now carry the value).

### 3.3 The format instruction (D8) and the repair request (D3)

One module, `workflow/output_format.py` **[proposal]**, builds both texts from the
step's declaration, so the first prompt and the repair request can never describe two
different shapes:

- `instruction(outputs, kind)` — appended to the first prompt:
  - with `outputs`: "Reply with ONLY one JSON object — no introduction, no explanation,
    no code fence." + one line per field (`name`: type, and "one of […]" for an enum) +
    "Example:" + the example object;
  - with `kind` json/yaml/csv and no `outputs`: "Reply with ONLY the <kind> content
    itself — no introduction, no explanation, no code fence.";
  - otherwise empty (prose kinds have no machine format).
- `example(outputs)` — a valid JSON object: `str` "text", `int` 0, `float` 0.0,
  `bool` false, `list` [], `obj` {}, and an enum field takes its first allowed value.
- `repair_request(reply, verdict, outputs, kind)` — the repair turn's prompt:
  1. "Your reply is still not valid JSON." / "Your reply still does not match the
     required format: <reason>." (D3a);
  2. the faulty part (D3b):
     - JSON that does not parse: the text around the `JSONDecodeError` position. When
       the reply does not start with `{`, the text before the first `{` (the usual
       preamble);
     - a field problem: the field name, the value it got and what it must be;
     - YAML: the line of the parser's `problem_mark`; CSV: the rows whose column count
       is not the table's (the most common width; on a tie, the last row's) — and none
       when the parser itself gives up;
     - an empty reply (a turn that only called tools): "Your reply had no answer in it",
       and nothing to quote;
  3. the failed reply itself, quoted in full up to 16,000 characters, head and tail
     beyond that **[proposal]**. Quoting it, rather than pointing at "your answer
     above", is what keeps a `map` element from repairing a sibling's answer (§1);
  4. the instruction above, including the example (D3c), and "Do not redo any work and
     do not call any tool; rewrite the answer you already have.".

### 3.4 The repair turn (D1)

`agent_write_step` builds `repair(verdict)` from the last attempt's reply text:

- `drive_turn(repair_request(...), [])`, i.e. the same lane, chat and turn machinery
  (quota, stop, persistence) as the step itself, with an empty tool list. `[]` means
  "zero tools" in the runner (`litellm_runner.py`, the tri-state on `allowed_tools`),
  but some tools are added by rules of their own (`read_skill`, the env-request card).
  P4 proves the repair turn really carries none and fixes it if not;
- then the same post-processing as a normal attempt: write `out`, parse `fields`.

### 3.5 The request in the workflow chat (D7)

The repair request is recorded in the workflow chat as a message with a new role,
`repair_request` **[proposal]**:

- not `notice`: `already_noticed` (`api/turns.py:129`) counts **any** `notice` as "the
  #624 context notice was already shown", so a repair recorded as one would silence that
  notice for the rest of the chat;
- not `user`: node prompts are not stored, so a stored repair request would be the only
  question in the history, and later nodes would read a request meant for another step.
  `history_items` replays only user / assistant / tool / summary (and a cancellation),
  so a new role is never sent to the model;
- recorded by a new optional handle hook, `WorkflowHandle.record_note`, wired by the
  executor. `sub_handle` copies the handle, so a `map` element records into the same
  chat. A handle without the hook (tests, other drivers) just does not record;
- the frontend renders it as a system line in the chat, labelled 「要求重新輸出格式」.

### 3.6 Events and the run log (D7)

- A new event, `StepRepairing(phase, name, reason, key, repair)`, type `step_repairing`,
  mirrored in `web/src/events.ts`; `repair` is its number, from 1.
- `StepState.status` gains `repairing` and a `repairs` count; `attempts` counts it like a
  retry.
- The chat's step line, the log view and the step board show 「修正輸出格式（第 n 次）」
  with the reason; the timeline shows it in the bar's title (its bar has room for the
  step name only); `retrying` keeps its current look and words.

## 5. Not changed

- **No sanitizing.** The platform still never strips a preamble or a fence (alignment
  plan D6); only the model rewrites its reply.
- **The steerer** (`workflow/steer.py`) keeps its own lenient parse and retry; it is not
  an agent step and is outside the user's question.
- **The Python API defaults.** `agent_write_step(retries=0)` stays one attempt, so a
  Python workflow gains only the format instruction (D8) unless it asks for retries.
- **Sandbox steps with `outputs`.** No model, nothing to repair; they keep failing as
  today.

## 6. As built (#973)

Where the build adds to or differs from the sections above; this section wins.

- **The repair turn's tools (P4).** `tools=[]` empties `allowed_tools`, but `read_skill` is
  granted by the item's skills, not by that list, so a repair turn on an item with a skill
  still held it. `build_workflow_turn` now withholds it when the subset is empty; a node
  that names any tool still follows the item's skills (the test checks both).
- **The workflow chat lookup (P5).** The turn and the recorded request resolve the chat
  through one function, `WorkflowExecutor._workflow_chat`, legacy fallback included, so
  the request can never land in a different conversation from its answer.
- **The usage bar (P5).** `context_budget._replayed` kept its own list of roles to skip,
  so it charged every role it did not name — the new `repair_request`, and the mention
  and goal markers before it — though the model never reads them. It and
  `history_items` now read one rule, `turns.replays`; a parity test holds them together.
- **The reasons carry the value (P3).** `_outputs_check` now says what it got: a wrong
  type quotes the value, a missing field lists the fields the reply had. The repair
  request quotes that as the faulty part, and the reason is made where the value is.
- **The disclosure (P5).** The chat folds the request behind a text button, copying the
  chat's existing summary fold (`CompactionSummary`), and adds what that fold lacks:
  `aria-expanded` and `aria-controls`. Control kind: a disclosure —
  [NN/g, *Progressive Disclosure*](https://www.nngroup.com/articles/progressive-disclosure/)
  (show the rare, long detail on request) and
  [W3C APG, *Disclosure (Show/Hide) Pattern*](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/)
  (a button with `aria-expanded`, controlling the region it shows).
- **A retry's words.** The grill called the unchanged state 「重試中」; the run log in fact
  shows `retrying` and `↻`, and that is what stays. Only a repair has new words.

### Review round 1 (on 44589200)

Four lenses; what they found and what changed:

- **The history windows charged what the model never reads.** `history_items` cut by
  count and tokens BEFORE filtering by `replays`, so a repair request (a whole quoted
  reply) dropped real history and persisted a false #624 notice. The filter now runs
  first: the windows and the usage bar charge the same messages.
- **A lost write.** The request was appended from a thread, a get-then-update with no
  etag; a parallel `map` element's persisted answer landing in between was overwritten.
  It is appended on the loop, like every other writer to the chat.
- **Whose check is repaired.** `artifact_valid` flagged a parse failure for any file; an
  author's check of a file the agent wrote with its tools then got a no-tools repair that
  could not work. Only the reply's own `out` (`of_reply`, set by `agent_write_step`'s
  default gate) is repaired.
- **CSV.** A field past the parser's limit made building the request raise; a tie between
  a one-line preamble and a one-row table quoted the data row. Both fixed (§3.3).
- **A node with `tools=[]`.** Withholding `read_skill` for an empty subset (P4) applies to
  every node that asks for no tools, not only a repair turn — a Python `run.py` the
  scaffold wrote with `tools=[]` (its own comment already says that means NO tools). Kept:
  an empty list is the runner's "explicit zero"; the runbook entry says so. The DSL maps
  `tools: []` to the item's tools and is unaffected.
- **The words.** The timeline now names a repair; the board's clock ticks while one runs;
  the fold and the log line go through i18n; the missing-field reason lists at most 20
  names; the runbook's old-image tell is now something an operator can see, and it states
  what a repair costs.
- **Known, not changed.** The compaction summariser reads every role, so a repair request
  can reach a summary (notices and mentions already do). A repair request is recorded
  before the turn's Stop and workspace-full checks, so a run stopped at that moment leaves
  a request with no answer under it. The P3 commit says quoting the reply means a `map`
  element "never" repairs a sibling's answer; it makes that unlikely, not impossible —
  the repair turn still reads the shared chat.
