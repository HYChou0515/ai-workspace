# 自架模型在 proxy 後面時,窗口上限解不出來

> 這份計畫處理的是 #624 那套「上下文窗口解析階梯」在**一個真實拓撲下四段全滅**的問題。
> 每一段為什麼答不出來,都在使用者的正式環境上量過,不是推論。

---

## 1. 症狀

使用者回報「自動 compact 好像有問題」。查下來**自動壓縮沒有缺陷** —— 它從來沒有執行過。

`plan_for_budget` 的第一行:

```python
if not force and (budget is None or used <= budget):
    return CompactionPlan(0, [], refusal="fits")
```

**沒有已知上限 ⇒ 直接回 `fits` ⇒ 自動壓縮不執行。** 歷史也不裁切(#624 的規則:寧可全送,
也不照猜的數字截肢)。這是刻意的設計,但從外面看跟「壓縮壞了」一模一樣,而且**沒有任何地方
告訴操作員自己處在哪一種狀態**。

### 迴圈是怎麼閉合的

```
上限 unknown
   ↓
自動壓縮不執行、歷史不裁切 → 每輪送出整串對話
   ↓
prompt 越來越大 → prefill 超過 TTFT 門檻(預設 8 秒)
   ↓
被判成「這個模型忙」→ provider 罰站 30 秒 → failover
   ↓
因為是 timeout 不是 400,撞牆學習永遠不被觸發 → 上限永遠 unknown
```

手動按壓縮之所以有效:prompt 變小,prefill 回到門檻內。使用者的原話是
「送會出事,但是先 compact 再送就好了」—— 那正是這個迴圈的外顯。

---

## 2. 為什麼四段階梯全滅

拓撲是 **app → litellm proxy → 自架 vLLM**,而且**模型名字是任意別名**。

| 階梯 | 結果 | 依據 |
|---|---|---|
| 1. `history.context_limit` | 沒設 | 使用者以 SSOT 為由否決(見 §3.1) |
| 2. 從流量學到的 | 空 | log 無 `truncated silently`;`/context` 回的 `limit` 是 `null` |
| 3. `/tokenize` 探測 | 沒答案 | log 無 `context probe`。`/tokenize` 是 vLLM 的擴充,**proxy 沒有這條路由** |
| 4. 模型登錄表 | `None` | 名字是任意別名。對照組正常:`gpt-4o-mini` → 128000、`ollama_chat/qwen3:14b` → 40960 |

⇒ `unknown`。

### 一個代價高的錯誤,記在這裡

第 2 段曾經被量成「拒絕但不講數字」,據此寫進文件說「這個部署學不到上限」。**那次量測是在
模型停機期間跑的** —— 一個停機中的端點回的錯誤裡當然沒有上限,長得跟「拒絕但不講」一模一樣。
重跑之後:**拒絕訊息確實帶著數字,解析得出來。**

> **停機中的服務會給你一個看起來完全合法的否定答案。** 任何探測在下否定結論之前,
> 要先確認對面是活的。

## 3. 被否決的做法

### 3.1 在 aiw 設 `history.context_limit`

**否決理由(使用者):違反 SSOT。** 正確 —— 那是一份 `--max-model-len` 的副本,改了本體而
忘了改副本就靜默漂移。

⚠️ 順帶推翻了一個中途的建議:「請同事在 proxy 補 `model_info.max_input_tokens`」也是副本,
只是離本體近一點。SSOT 管的不是「誰寫的」,是**有沒有第二份會跟著漂移的東西**:

| 來源 | 是副本嗎 | 改了 `--max-model-len` 之後 |
|---|---|---|
| `--max-model-len` | 不是,vLLM 拿它執行 | — |
| 拒絕訊息裡的數字 | 不是,讀自執行方、當下產生 | 自動跟上 |
| proxy 的 `model_info` | **是**,手維護 | 靜默漂移 |
| aiw 的 `context_limit` | **是** | 靜默漂移 |

### 3.2 自己帶一份模型目錄(OpenCode 走這條)

**否決理由:名字是任意別名,任何目錄都對不上。**

順帶查證了一件反直覺的事:**OpenCode 的規則跟本專案一模一樣。** 它的判斷是

```js
if (H.model.limit.context === 0) return false;   // 沒有窗口就不壓縮
```

保留額度也是同一個形狀(`min(20000, maxOutputTokens)`),沒有窗口時連百分比都不顯示。
使用者後來確認**他們的 OpenCode 也沒有在自動壓縮** —— 同一個根因。

所以「別人有解我們沒解」不成立,差別只在**目錄厚度**(models.dev 收了 GLM,litellm 的沒有),
而任意別名讓兩者都失效。

### 3.3 主動撞牆(送一個過長的請求,從拒絕訊息讀出上限)

技術上可行(§2 已證實拒絕訊息帶著數字),而且**沒有任何副本** —— 數字讀自執行方。

**否決理由(使用者):「不要為了繞過一個缺失的設定值而一直往 app 加機制」。** 這是產品判斷,
不是技術判斷,記錄下來以免日後有人重新提案時以為沒討論過。

### 3.4 拿 `max_tokens` 當**主要**來源

`max_tokens` 不是窗口。對照 litellm 自己的登錄表實測:

| | `max_tokens` | 真實窗口 | 比值 |
|---|---|---|---|
| gpt-4o | 16,384 | 128,000 | **7.8×** |
| gpt-4o-mini | 16,384 | 128,000 | 7.8× |
| ollama_chat/qwen3:14b | 40,960 | 40,960 | **1.0×** |

任何固定係數在另一個模型上就錯 8 倍。所以它**不能**當主要來源。

## 4. 定案:補第五段,而且只當 fallback

使用者的框架是**「補上 fallback」**,而這改變了計算:這一段只在其餘全部沉默時生效,
而那個狀態不是中立的 —— 是「完全不壓縮 → 送不出去」。所以比較對象不是
「正確的數字 vs 錯的數字」,是**「什麼都不做 vs 一個近似的天花板」**。

### 4.1 問 proxy 自己的 `GET /model/info`

litellm 的管理路由,回它**被設定成什麼**。兩件事要分開:

- **`max_input_tokens`** —— 就是輸入窗口,**直接採用,不乘任何係數**
- **`max_tokens`** —— 只有它有值時才乘係數當**估計**

⚠️ 探測**原樣回傳兩個數字**,不在探測裡解釋 `max_tokens`。在那裡乘係數等於
**把一個猜測藏進一個看起來像量測的東西裡**。要不要用、怎麼用,是階梯的決定。

⚠️ **兩種 url 拼法都要問**:`base_url` 是操作員寫的,聊天路由在 `/v1` 底下所以通常帶著,
但 litellm 把管理路由掛在 `/model/info` **和** `/v1/model/info`。只問一種,這一段就會
因為一個沒人在意的路徑尾巴而時靈時不靈。

### 4.2 排序與來源標記

```
你設的 → 從流量學到的(含 /tokenize) → proxy 宣告的 → 模型登錄表 → 估計 → unknown
  config        learned                    declared        catalog     estimated
```

- **`declared` 在 `catalog` 之上**:它是關於**這個端點**的陳述,而登錄表是按模型名字查的,
  那個名字端點自己未必認。
- **`estimated` 在所有明確數字之下**,包含 `catalog` —— 登錄表至少對它所指名的模型是精確的。
- **來源必須可分辨。** 一個沒人講過的數字絕不能讀起來像量測 ——`learned` 帶著
  「端點真的這樣做了」的權威,估計一點都沒有。

### 4.3 ⚠️ 估計絕不能進 `LimitLearner`

`/tokenize` 的探測結果目前是灌進 `LimitLearner.learn_exact` 的,而那個 store 的契約寫著:

> `learn_exact` —— a rejection stated the limit. **That is a fact; take it.**

把估計放進去,下游就再也分不出事實與估計,而 `ContextLimit.source` 會回報 `learned`。
所以估計必須是獨立的一段、獨立的來源名稱。

### 4.4 係數

`history.max_tokens_window_ratio`,**預設 0.8**,從 config 讀而不是寫死。

⚠️ 只作用在 `max_tokens` 那條路。`max_input_tokens` 已經是輸入窗口,再乘就是**扣兩次**
—— app 本來就會自己扣掉系統提示、tool schema、回覆保留額度和邊界。

## 5. 這個 PR 不做的事

- **TTFT 誤判**(§1 迴圈的第三格):固定 8 秒的門檻把「prompt 長」誤讀成「模型忙」,
  罰站一個健康的端點,而且什麼都學不到。**修法不能是「timeout 觸發壓縮」** —— timeout
  天生分不出「長」「忙」「暫時不可用」,而壓縮是有損且不可逆的。
  > **壓縮只能由「大小」觸發,永遠不能由「失敗」觸發。**
  > 大小在送出前就知道且確定;失敗在送出後才知道且分不出原因。
  這條原則值得寫進程式碼,但屬於另一個 PR。
- **OpenCode 那邊**:它不讀 `/model/info`(binary 裡沒有這個字串),所以要在它自己的設定裡
  各自宣告一次。不是這個 repo 的範圍。
- **文件 PR #758** 已經在描述今天的階梯;本 PR 落地後要更新那張表。
